# r41 Mac 연결 직후 저하 — MLO/6GHz 비교

2026-09-27, 현재 MacBook과 같은 r41 부팅에서 각 40초 다운로드를 측정했다. **두 모드 모두 첫 500Mbps 미만 구간이 연결 후 약 22초에 나타났다.** MLO 전용 증상으로 한정할 수 없고, iperf 시작 직후의 일반적인 TCP 준비 지연으로도 설명하기 어렵다. 새 제품 패치나 r42는 만들지 않았다.

## 관측 결과

|---|---:|---:|

| 500Mbps 미만 1초 구간 / 0Mbps 구간 | 14 / 0 | 7 / 0 |

| macOS BEST CONNECTED 스캔 요청 | 약 20.28초 | 약 20.26초 |
| 초반 정상 전송 | 0–13초 평균 1957Mbps | 0–10초 평균 1894Mbps |

시작 시각은 클라이언트 프로세스 시작과 종료/수신 지속시간으로 잡은 보수적 범위다. association 나이는 공유기 부팅 시계와 왕복 조회로 연결했다. 구간 경계의 소수점 반올림 때문에 일부 범위가 약간 넓다. 동일 시간대의 반복 무작위 비교가 아니므로 두 평균의 차이를 모드별 우열이나 개선률로 해석하지 않는다.

## 좁혀진 원인

- **초기 BA 준비 지연 가설은 이번 재현과 맞지 않는다.** TID0 ADDBA 성공 응답과 양 MLO 링크의 TX BA MCU 성공은 연결 0.474초 안에, 단일 링크는 0.360초 안에 관측됐다. 이후 iperf 초반은 이미 고속 전송됐다. 이는 호스트의 협상/명령 경로 완료 증거이며 모든 무선 BA 전달의 보장은 아니다.
- iperf를 약 3–4초 다른 연결 나이에 시작했지만, 저하는 두 모드 모두 연결 후 약 22초에 나타났다. macOS가 연결 직후 예약한 **20초 BEST CONNECTED 스캔**, 절전 상태, 재전송 증가의 연관성이 강해졌다. scan API 시작/끝은 실제 RF 체류 시간과 같지 않다.
- MLO에서 전역 PS 알림 내부 누락 105개가 있었고, 관측한 대상 PS 557개는 모두 `gate == primary_ps && secondary_ps`였다. 관측된 host TXQ gate가 두 링크 상태와 어긋났다는 증거는 없다. 단일 링크는 기존 PS trace가 수집 대상에서 제외하므로 이벤트 0을 절전 전환 없음으로 해석하지 않는다. 단일 링크 저하 스냅샷에서는 PS=1이었다.
- 재전송은 MLO TCP 13–14초 1049회/14–15초 5220회, 단일 링크 10–11초 1572회/11–12초 4189회로 증가했다. 이후 TCP 혼잡 윈도 축소가 회복을 늦추는 흐름과 일치한다. 재전송 수는 RF 손실 위치나 패킷 폐기 원인을 직접 알려주지 않는다.
- TXFREE 상태2는 상위 MediaTek 자료의 RED drop 분류와 대응하지만, 누계는 TXFREE HEADER 수다. 개별 TCP 패킷 손실·NPU 오류 횟수와 같지 않다. Wi-Fi 펌웨어 내부의 폐기 조건과 공통 PPE/NPU 경로의 영향은 미확정이다.

따라서 BA 재시도나 host PS gate를 임의로 바꿀 새 근거는 없다. 다음 조사 대상은 스캔/절전 중 공통 송신 경로에서 폐기가 늘어나는 조건이며, 원래 Air의 절전 복귀 멈춤을 이번 Mac 시험으로 해결했다고 판단하지 않는다.

## 경로·복원 검증

두 시험 모두 실제 TCP 데이터 연결 4개가 PPE에 등록된 시점별 자료, 동일 association, 시험 전후 설정/부팅 유지, 유선 HTTP 확인 각 55회가 통과했다. 이는 패킷 전부의 연속 경로를 증명하지는 않는다. 6GHz 전환 제어기의 추가 유선 확인은 119/119 정상이었다.

단일 링크 비교는 기존 검증된 절차로 무선 세 항목과 가속 포트 하나를 일시 전환했다. network/firewall 내용은 유지했고 종료 후 wireless·bridge-flow-offload·network·firewall 네 원본 해시, 원래 MLO 가속 포트, 같은 부팅을 검증했다. PS/BA/awake 진단 옵션은 모두 OFF, Mac은 기존 iPhone 핫스팟으로 복원했고 en0에 묶은 HTTPS 응답 200을 확인했다. 펌웨어 설치나 재부팅은 하지 않았다.

## 기록 한계

단일 링크의 추가 종료 queue/AP-info 스냅샷은 wrapper 연결 누락으로 생성되지 않았다. 기본 station.after 기록과 설정/부팅 검증은 남아 있으나 종료 WCID·mask·최종 상태2 누계는 미관측이다. 종료 후 wrapper를 수정했으며 누락 자료를 재구성하지 않았다. 상태2는 시험 전/저하 중(및 MLO 종료 후) 스냅샷만 있어 초 단위 발생률이 아니다.

방출된 kernel record의 sequence와 전송 해시는 검증됐다. 이는 rate-limit으로 애초에 방출되지 않은 이벤트를 복원하지 않는다. iperf 전에는 연결 검증용 HTTP가 있었으므로 ‘첫 Wi-Fi 데이터’ 시험도 아니다. 암호·백업·단말 식별자·원시 패킷은 공개 결과에서 제외했다.

## 공식 자료 대조

Apple은 Apple silicon Mac의 802.11k/v 지원, Neighbor Report를 통한 탐색 채널 축소, RNR을 이용한 6GHz 발견을 설명한다. 그러나 이번 로그의 BEST CONNECTED 20초 예약 동작을 이 문서의 RSSI 기반 로밍 조건과 동일시할 근거는 없다. [Apple Wi-Fi 로밍 지원 문서](https://support.apple.com/guide/deployment/wi-fi-roaming-support-dep98f116c0f/web).

보존된 AP 설정에는 k/v 관련 명시 옵션이 없지만, 현재 hostapd는 co-located/MLO 조건에서 RNR을 자동 생성하는 경로가 있다. 따라서 설정에 rnr 옵션이 없다는 사실을 RNR 미광고로 해석하지 않는다. Neighbor Report 설정은 실제 광고/요청을 확인한 뒤 검토할 후보이며 이번에는 변경하지 않았다.

두 native 기록에서 완료된 캐시 보조 background scan 요청은 각각 33회였고, 요청 채널 목록과 순서는 동일했다(2GHz 13개 + 5GHz 25개 + 6GHz 59개 = 97개). 요청별 보고 시간 합은 MLO 11.807초, 단일 6GHz 13.3146초다. 전 채널 실제 RF 체류 시간이나 Neighbor Report 미사용의 증거는 아니다. 현행 AP의 읽기 전용 `show_neighbor` 응답은 양 링크 모두 FAIL이었으므로 이 조회로 NR 내용을 확보하지 못했다. RRM을 활성화하는 ubus 조회 메서드는 사용하지 않았다.
