# r46 MLO 하향 처리량 저하 관측 (2026-10-07)

r46을 설치한 장치와 Mac(6 GHz 160 MHz, EHT-MCS 11 NSS 2, 2401.9 Mbps)으로 iperf3 하향 4흐름을 30–40초씩
약 30회 반복했다. 흐름은 PPE·NPU로 하드웨어 오프로드된다. 원인을 고친 기록이 아니라 관측 기록이다.

## 결과

- 회차는 두 갈래다. 빠른 회차는 1,920–1,980 Mbps, 서버 재전송 1.5–3천 회. 느린 회차는 970–1,460 Mbps,
  재전송 5천–2만 회이고, 1,100–1,250 Mbps에 오래 머물거나 몇 초 동안 0–500 Mbps로 떨어진다.
- 트래픽은 내내 6 GHz 링크(band 2)로만 나가고 PHY 속도도 그대로다. 느린 구간에는 같은 속도에서 성공 MPDU가
  초당 약 2.5만에서 1.5만으로 줄었다.
- 6 GHz 채널 survey: 빠른 구간은 AP 송신 시간이 활성 시간의 약 90%, 느린 구간은 28–65%. 다른 기기의 수신
  점유는 어느 쪽이든 약 5%라, 채널이 비어 있는데 AP가 보내지 않는다.
- 라우터의 netdev 드롭 카운터(eth0, lan2–4, br-lan, ap-mld0)는 0, band 2 송신 실패는 시도의 약 0.1%.
- `ps_trace`를 켜고 잡은 느린 회차에서 저하는 Mac의 절전 전환이 시작된 순간과 정확히 겹쳤다. 15초까지
  P 이벤트 0회·약 1,950 Mbps였고, 15초부터 두 링크(link 1·2)에서 초당 약 16회(기록 기준, 속도 제한 있음)
  절전 진입·해제가 반복되며 16–18초는 0 Mbps, 이후 1,050–1,280 Mbps였다. 빠른 회차 4번의 P 이벤트는
  회차당 4–16회였다.
- macOS 시스템 설정의 Wi-Fi 화면을 연 채로 측정하면 하향이 100 Mbps 아래로 떨어지는 구간이 생겼다.

## 해석과 남은 질문

- 저하의 시작은 단말(Mac)의 주기적인 절전 전환이다. 주기(초당 약 8쌍)는 AWDL(AirDrop·연속성) 채널 전환과
  맞고, 아래 비교에서 AWDL을 끄자 저하가 사라졌다.
- 단말이 자주 자리를 비우면 처리량이 줄어드는 것은 정상이다. 그러나 전환이 시작된 직후 3초 동안 0 Mbps였던 것은
  단말이 깨어 있는 순간에도 AP가 보내지 못했다는 뜻이며, 기존 MLO 절전 복귀 조사(0008, 0015)와 같은 영역이다.
  오프로드 경로의 절전 처리는 NPU·무선 펌웨어 안에 있어 호스트 카운터로는 보이지 않는다.

## AWDL을 끈 비교 (같은 날)

Mac에서 `sudo ifconfig awdl0 down` 뒤 같은 하향 시험 30초 × 8회:

| 조건 | 느린 회차(1,500 Mbps 미만 구간이 있는 회차) | 회차 평균 | 회차 최저 1초 | 회차당 Mac P 이벤트 |
|---|---:|---:|---:|---:|
| AWDL 켬 (이전 약 22회) | 13 | 970–1,980 Mbps | 0 Mbps | 느린 회차 300 |
| AWDL 끔 (8회) | 0 | 1,852–1,969 Mbps | 1,501 Mbps | 4–20 |

상향 30초는 평균 1,768 Mbps(최저 1,564)였다. 저하를 일으킨 것은 Mac의 AWDL이 만든 주기적 절전 전환이다.
라우터 쪽에 남는 과제는 전환이 몰릴 때 몇 초씩 0 Mbps가 되는 복귀 지연이다(AWDL은 macOS 기본값이라 실제
사용 환경에서 계속 일어난다). 처리량 시험은 AWDL을 끄고 하거나, 켠 상태의 결과를 따로 구분해 적는다.

## 손실 위치 (같은 날 추가)

Finder의 AirDrop 창을 열어 두면 AWDL이 활성화되어 저하를 매번 재현할 수 있다. 각 30초 하향, 6 GHz 링크의
송신 완료 상태(`mt76/hw-queues`의 `txfree_status`, `MT_TXFREE_INFO_STAT`) 증가량:

| 조건 | 회차 평균 | 0 Mbps 초 | 상태 1 | 상태 2 |
|---|---:|---|---:|---:|
| 오프로드, AWDL 유휴 (8회) | 1,903–1,988 Mbps | 없음 | 0 | 0 |
| 오프로드, AirDrop 창 열림 (3회) | 993–1,225 Mbps | 있음 | 198–768 | 1,676–5,861 |
| CPU 경로(`bridge-flow-offload` 끔), AirDrop 창 열림 (3회) | 1,130–1,194 Mbps | 없음(최저 922) | 0–144 | 0 |

CPU 경로는 원래 1.1–1.2 Gbps가 한계라 평균은 비교하지 않는다. 같은 절전 전환에서 CPU 경로는 mac80211이
프레임을 붙잡아 상태 2 손실과 멈춤이 없고, PPE→NPU 경로에서만 상태 2 손실과 TCP 재전송 시간 초과(0 Mbps)가 생긴다.

NPU 펌웨어 재구성 소스(ClankerNPU)와 mt76·커널 소스를 검토한 결과(Codex):

- 상태 값은 NPU가 아니라 MT7996의 TXFREE 경로가 보고한다. 드라이버는 0이 아닌 값을 모두 실패로 센다.
  2가 절전 단말 거부를 뜻한다는 정의는 소스에서 찾지 못했다(측정상 추정).
- 재구성된 NPU 송신 경로에는 단말 절전 상태를 보고 프레임을 붙잡거나 다시 보내는 처리가 없다.
- 호스트가 보낼 수 있는 `ERROR_RETRY_TIMES`는 NPU 내부 enqueue 재시도이고, `FLUSHONE/FLUSHALL_TIMEOUT`은
  이 펌웨어 변형(Eagle)에서 "not support"로 끝난다. 배포 바이너리의 버전 문자열은 `TLB7.7.0.0_v03`이고 재구성
  소스는 `TLB7.8.0.0_v003` 기준이라 동작을 확정하지 않는다.
- mt7996 소스에서 단말·AC별 송신 수명이나 재시도 한도를 바꾸는 MCU 명령은 찾지 못했다.

따라서 지금은 안전하게 바꿀 수 있는 값이 없다. 다음 후보는 (1) 절전 전환(`P` 이벤트)에 맞춰 해당 단말의
오프로드 흐름을 잠시 CPU 경로로 돌리는 호스트 정책, (2) NPU가 쓰는 TXD의 수명·재시도 필드를 확인하는 것이다.

원시 기록(단말 MAC 포함)은 공개 저장소에 넣지 않았다.
