# Air r32 기존 기록의 계측 범위 재검토 — 2026-09-26

기존 세 회차의 기록만 읽었다. 새 무선 시험·공유기 접속·공개 소스 변경은 없다. Mac 성공 회차를 Air 실패 회차의 대조군으로 사용하지 않았다. 원시 단말 식별자·주소·패킷 내용은 이 보고서에 포함하지 않는다. 입력 경로와 SHA256, 계산 수치는 `AIR_EVIDENCE.json`에 보존했다.

**사용자가 본 MLO 멈춤은 미해결이며, 저장 자료만으로 전역 NPU worker 정지와 단일 peer의 ACK·스케줄 정체를 구분할 수 없다.** 기존 원인 미확정 결론을 뒤집는 증거는 없다. 다만 slow 표본의 시각은 실제 항목을 읽은 시각이 아니라 수집 시작 시각이라는 한계를 더 정확히 정량화했다.

## 비교한 세 회차

| 회차 | 사용자 평균/최저/최고 Mbps | 사용자 관측 | LAN 집계 최저 구간 | 빠른/상세 표본 |
|---|---|---|---|---|
| MLO 절전 복귀 | 1914 / 0 / 2041 | 잠깐 멈춤 | T+21.48–22.51초, 184.661 Mbps | 500 / 100 |
| 단일 6GHz 절전 복귀 | 1860 / 410 / 2034 | 속도만 낮아짐 | T+7.16–8.18초, 0.0714 Mbps | 500 / 100 |
| MLO 절전 복귀, PS 로그 ON | 1715 / 1336 / 1987 | 멈춤 없음 | T+204.76–205.79초, 1352.860 Mbps | 500 / 100 |

T는 앱 시작이나 잠금 해제 시각이 아니다. LAN2 전체 입력량이 100 Mbps를 넘은 첫 구간의 시작을 이용한 추정 기준이다. 사용자 멈춤 시각과 앱 원시 초별 기록이 없으므로 MLO의 집계 최저 구간을 바로 그 멈춤이라고 확정하지 않는다. 각 회차의 292개 내부 구간은 각각 298.79 / 298.77 / 298.95초이며 양끝 약 2.03 / 2.04 / 2.04초의 부분 구간을 제외한다. LAN 전체 바이트는 Air 애플리케이션 goodput이 아니다.

## 시간 정렬과 놓치는 구간

- 같은 부팅의 `/proc/uptime`을 SAMPLE/END에 기록했고 시간 표기는 0.01초 해상도다. 빠른 표본 간격은 약 1.02초이고, `/proc/stat`·`/proc/net/dev`·carrier 읽기 자체도 0.01–0.03초에 걸친다.
- MLO 실패의 slow 시작 간격은 5.62–5.72초(중앙 5.66초), 수집 시간은 0.62–0.71초다. 수집이 전혀 없는 간격은 5.00–5.01초다. 단일 6GHz는 시작 간격 5.63–5.82초, 수집 0.62–0.81초이며 PS 로그 회차는 각각 5.63–5.80초, 0.62–0.80초다.
- MLO 최저 구간 중심보다 0.495초 뒤라는 기존 수치는 **slow 시작 marker**의 거리다. 실제 PC·PS·PPE 읽기는 T+22.49–23.13초 안에 순차 실행됐다. 기록된 시작 marker끼리 비교하면 집계 최저 구간 끝보다 0.02초 앞서 수집을 시작한 셈이며, 일부 읽기는 구간 종료 뒤였을 수 있다. 빠른 counter 자체의 읽기 오프셋과 0.01초 시각 해상도가 추가 불확실성이므로 정확한 겹침이나 항목별 시간은 확정하지 않는다.
- 단일 6GHz 최저 구간은 앞 slow 수집 종료 T+5.62초와 다음 시작 T+10.63초 사이에 완전히 들어간다. 앞뒤 PS0·PPE 정상 표본으로 그 사이 상태를 증명할 수 없다.
- 실패 MLO의 6GHz PS1 표본은 T+16.81–17.49초와 T+300.61–301.23초에 있었다. 두 번째는 시험 끝부분/경계를 가로지른다. 첫 번째 이후 PS0이 관측된 T+22.49–23.13초까지의 정확한 전환 시각이나 PS1 지속 시간은 기록하지 않았다.
- PS 로그의 kmsg 시간은 같은 부팅의 host 알림 시각이다. 7.539ms PS1→PS0 간격은 host 알림 간격이며 실제 무선 상태의 지속 시간을 보장하지 않는다. 로컬 제어기의 epoch도 앱 시작 시각이 아니며, 이 세 회차에는 서버 TCP 시계와의 정렬 자료가 없다.

## CPU·PPE·NPU·큐가 말해 주는 범위

MLO 최저 bin의 CPU 전체는 3.951%, 가장 바쁜 코어는 6.796%다. 단일 6GHz 최저 bin은 전체 4.680%, 가장 바쁜 코어 6.796%다. 해당 약 1초 bin 전체에 걸친 CPU 포화로 저하를 설명할 수는 없지만 그보다 짧은 지연까지 배제하는 값은 아니다. 기존 전체 평균 CPU도 상세 표본 끝점 사이인 295.13 / 295.46 / 297.19초를 적분한 값으로 전체 추정 시험 길이와 정확히 같지 않다.

각 회차의 시험 내부 PPE 등록 검사는 52/52 정상이다. 이는 네 흐름·양방향 8개 binding의 존재를 확인한 것이며 실제 packet progress·ACK·동시 무효화·firmware 실행을 확인한 것은 아니다. selector와 WCID 역시 표본들에서 같았으므로 짧게 바뀌었다 돌아온 경우를 배제하지 못한다.

NPU PC는 세 회차 모두 hart당 53개, 8개 hart를 합쳐 424 register word다. 각 hart도 순차 읽었으며 연속 추적이 아니다. 의심 대기 PC가 없다는 관측으로 약 5초 공백 안의 정지를 배제할 수 없다. `token_count`는 host SW in-flight 값이고 표본 범위는 각각 3–11 / 3–30 / 3–102다. NPU firmware token pool 사용량을 읽은 값이 아니다. `token_info`와 `hw-queues`는 있으나 qdisc backlog, 공유 TXQ active-list 연속 상태, RRO session 생명주기 기록은 없다.

## 다른 peer가 동시에 진행했는가

MLO 최저 fast bin에서 비대상 2.4GHz netdev의 증가는 TX 1 packet·78 bytes뿐이다. 제어/host 경로일 수 있어 NPU fastpath 진행 증거로 사용하지 않는다. 같은 bin의 MLO netdev 변화도 전체/host-visible 카운터이며 Air나 특정 다른 peer의 ACK 진행으로 귀속할 수 없다.

인접 slow 표본(T+16.81 및 22.49, 전체 읽기 경계 T+16.81–23.13초) 사이 다른 peer의 5GHz TXS 15·정상 숫자 상태 17 및 또 다른 peer의 6GHz TXS 54·정상 숫자 상태 66 증가가 있다. 그러나 이 차분은 1.03초 저하보다 긴 구간을 포괄하며 `tx_prepared`도 각각 17/90 증가한 혼합 경로다. 증가가 저하 전후에 몰렸을 가능성과 제어 트래픽을 배제할 수 없다. 단일 6GHz 최저 bin의 비대상 radio 카운터 증가 역시 수 KB 수준의 host-visible 값으로 동일한 한계를 가진다. **동시 다른 peer의 NPU fastpath 유효 데이터 진행을 보여 주는 대조는 확보되지 않았다.**

## PS 상세 로그의 실제 coverage

실패 MLO 회차는 PS trace OFF였다. PS trace ON 회차는 멈춤이 없었으며 성능 수치도 진단 OFF와 인과적으로 비교할 수 없다. 저장 kmsg의 앞선 과거 기록 612개를 제외하면 begin/end 경계의 1,540개 sequence가 연속이고 파일 해시도 일치한다. 이는 emit된 로그의 보존 확인이다.

그 회차의 Air status1 카운터 증가 31개 중 상세 F는 8개(25.81%)뿐이며 23개(74.19%)는 세부 정보가 없다. 카운터와 상세 로그의 끝점도 원자적이지 않아 이 비율을 정확한 logger 누락 확률로 해석하지 않는다. 숫자 status2 475개도 멈춤 없이 증가했고 상세 status2 로그는 원래 대상이 아니다. 내부 sequence에 gap이 없다는 사실은 rate limit·출력 gate로 emit되지 않은 이벤트를 복원하지 않는다.

## 결론의 한계

세 회차에 per-client TCP sequence/ACK/retransmit 타임라인, 앱 원시 초별 값, 사용자 멈춤 시각이 없다. qdisc와 TXQ 스케줄 이력, NPU hardware token 사용량, RRO/firmware 실행 추적도 없다. 따라서 이번 오프라인 재검토는 CPU 포화 가설의 범위를 줄이고 기존 계측의 공백을 명확히 하지만, r35의 링크 전환 수정이나 새로운 NPU 가설이 Air 멈춤 원인이라는 증거를 추가하지 않는다. 새 시험을 수행한 결과로 읽어서는 안 된다.
