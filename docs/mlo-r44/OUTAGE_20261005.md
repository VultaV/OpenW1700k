# r44 전 대역 Wi-Fi 재연결 장애 — 2026-10-05

## 결론과 조사 범위

**인증 완료 전 재접속 반복은 확인되지만, 최초 원인은 확정할 수 없다.** 전체 칩/IRQ 정지나 host TX token 고갈은 뒷받침되지 않으며, 연결 승인 전 교환의 일부 경로 실패가 의심된다. NPU TX, 무선 firmware, hostapd 상태 중 어디서 최초 실패했는지는 아직 구분되지 않는다. 기존 Air MLO sleep/wake stall과 같은 원인이라고 간주하지 않는다.

- 사용자 보고: r44, 약 58시간 가동 후 23:43경부터 약 17분간 2.4 GHz legacy와 5+6 GHz MLD의 모든 단말에 영향. `wifi` 후 handshake/DHCP 즉시 회복. 재시작은 hostapd·STA·driver/firmware 상태를 함께 바꾸므로 원인 분리 시험이 아니다.
- 증거: 비공개 `.evidence/state.sanitized.txt`, 1,078행, SHA256 `83b052781948b1a64d99fcac9e5baac63fbede8ac6186248b08f8eee759af555`. 아래 `L`은 이 파일 행번호다. 발단과 재시작 후 정상 자료는 없고, logread는 **23:58:17–00:01:25**만 남았다. 보고의 약 17분과 별개로 이 tail에도 장애가 계속 보인다.
- L2 `209026.75 818090.74`: uptime 약 58시간 3분. 두 IRQ 표의 간격 3초는 수집 설명에 따른다. 그 외 출력은 순차 수집이며 동시·주기 표본이 아니다.
- [r44 빌드 기록](BUILD_RESULT.json)은 모듈 74개, firmware 11개, wpad가 r43과 동일함을 기록한다. 커널 코드는 동일하고 FIT metadata는 달라질 수 있다. r44 전용 driver 회귀라고 부를 근거가 없다.
- [인계서 1·5·6·7절](../CLAUDE_HANDOFF_20261003.md), mt76 `01367e60db433534ad0aa3d3b6c886de8cb7d44c` 및 현 패치, hostapd `831364bf02710ad09c2f27d3efa92abeeb5634c0` 및 현 패치를 대조했다. 마운트된 r43 prepared source도 확인했다. 공유기 접속·설정 변경·빌드·설치·push 없이 문서만 추가한다.

`MAIN0`에는 미회수 descriptor 하나가 있다. 바로 앞 `token_info`와 같은 값인 것은 장시간 고정 증거가 아니다. `hw-queued/head/tail`은 host의 `q->queued/head/tail`이며 WFDMA의 실시간 CIDX/DIDX가 아니다. 입력이 있는 동안 계속 고정되는지 재측정해야 한다. SW token 35개로 pool 고갈을 주장할 수 없고, **firmware 소유 HW token의 사용 개수는 없다.** 낮은 사용량만으로 stale queue-block flag까지 배제하지는 못한다.

RX `queued=ndesc-1`은 `mt76_npu_fill_rx_queue()`가 공급한 수신 buffer 수다. backlog 511개로 읽으면 안 된다. L188–203의 다른 RX ring도 단일 host snapshot이며 고정 index만으로 정체라고 판정하지 않는다.

`tx_stats`의 원문 `Tx attempts`/`Tx success`는 band0 `580135/526406` (L111–112), band1 `2997023/2573874` (L138–139), band2 `6125914/5841339` (L165–166)다. 누적치 한 벌이므로 표시 PER 10/15/5%는 장애 3초의 손실률도 송신 진행 증거도 아니다.

## 2. hostapd 메시지가 뜻하는 단계

기준은 단순한 “2.11” 일반론이 아니라 [package recipe](../../package/network/services/hostapd/Makefile)의 pinned source다. [OpenWrt source archive](https://sources.openwrt.org/hostapd-2026.08.07~831364bf.tar.zst)의 SHA256은 recipe의 `d1b9ca0e6aaaba928fc5d5b02c0084083e745a38ae1214d0e2dc5d1ea6d50393`와 일치했다. 현 패치 적용 결과와 r43 prepared source의 관련 파일도 대조했다. 아래 함수명은 그 소스 기준이다.

**`deauthenticated due to local deauth request`는 원인 코드가 아니다.** `src/ap/sta_info.c::ap_handle_timer()`의 `STA_REMOVE`에서 출력한다. `ap_sta_disconnect()`가 driver deauth를 먼저 요청하고, `AP_MAX_INACTIVITY_AFTER_DEAUTH=5`초 뒤 정리할 때 남길 수 있다. CLI/ubus 요청도 이 경로에 들어올 수 있으므로 메시지 하나로 사용자의 강제 해제나 RF 실패를 판정하지 않는다.

| 진입 경로 | 소스 흐름·시간 | 이번 자료와의 관계 |
|---|---|---|
| WPA 4-way 실패 | `wpa_send_eapol_timeout()` → PTK retry 한도 → reason 15 (`4WAY_HANDSHAKE_TIMEOUT`) → `DISCONNECT` → `hostapd_wpa_auth_disconnect()` → `ap_sta_disconnect()` → `ap_sta_handle_disconnect()` → REMOVE. MLD는 `ap_sta_ml_disconnect()`로 partner/association STA를 정리 | 가장 잘 맞는 **실패 단계 후보**. 기본 pairwise update count 4, 첫 timeout은 TX status 지원 시 100 ms, 후속 1 s; 첫 ACK로 1 s 연장 가능. M1 무응답 시 대략 3.1–4 s 뒤 실패 + 정리 5 s. 설정/재association/스케줄링에 따라 달라짐. 미전송·무ACK·ACK 후 M2/M4 미수신·유효하지 않은 응답을 이 로그만으로 구분 불가 |
| inactivity / no-ACK poll | `ap_handle_timer()`가 기본 300초(+0–19초 fuzz, max-idle 설정)와 driver inactive time을 확인하고 NULLFUNC poll. `hostapd_tx_status()`/`hostapd_client_poll_ok()`가 ACK 시 pending을 지움. 3초 뒤에도 pending이면 DISASSOC, 1초 뒤 DEAUTH. 별도 `hostapd_event_sta_low_ack()`는 설정에 따라 `disconnected due to excessive missing ACKs` 출력 | 새 connection 3/7초와 기본 300초는 맞지 않음. 사용자 설정·오래된 timer/STA 재사용·driver low-ACK event는 미수집. 정상 inactivity 로그는 `disassociated/deauthenticated due to inactivity`여서 local-request 문구와 그대로 동일시하면 안 됨 |
| PMF SA Query | `ieee802_11.c::check_sa_query()` 및 `sta_info.c::ap_check_sa_query_timeout()`/`ap_sa_query_timer()`; pending query는 assoc를 잠시 거절, 만료는 재association 허용·기존 상태 정리와 연결 | MFP yes만으로 query 실행을 증명하지 못함. 기본 retry 201 TU, max 1000 TU(약 1.024 s)는 4-way timer와 다름. timeout 함수 자체는 timed-out flag와 query timer만 정리하며 STA_REMOVE/local-deauth를 직접 실행하지 않음 |

legacy의 실제 순서는 L1033 `00:01:04 ... associated (aid 1)` → L1041 `00:01:07 ... MLO disconnect result=0 wcid=3 link=0 sta=1 disabled=0` → L1051 `00:01:12 ... deauthenticated due to local deauth request`다. 주소와 고정 log prefix만 생략했다. **약 3초 실패 + 5초 cleanup과 일치하지만 reason code/EAPOL 단계가 없어 4-way timeout 확정은 아니다.** `MLO disconnect`라는 driver 로그 이름은 legacy WCID에도 쓰인다.

retained tail의 local-deauth 8건은 전부 `phy0.0-ap0`다. MLD는 `authenticated` 직후 다른 두 주소 X/Y의 `handle_assoc_cb: STA ... not found`가 교대로 남는다(L1038–1039,1048–1050,1056–1058; not-found 총 32건). 따라서 두 AP가 똑같은 단계에서 실패했다는 주장은 사용자 보고와 retained evidence를 구분해야 한다.

`ieee802_11.c::handle_assoc_cb()`는 **보낸 association response의 TX-status callback**이다. 수신 probe-request 경로가 아니다. `ap_get_sta(hapd, mgmt->da)`와 [194 link-address fallback](../../package/network/services/hostapd/patches/194-AP-find-MLD-stations-by-link-address-in-the-TX-statu.patch)이 모두 실패하면 해당 문구를 출력하고 return한다. 이 lookup은 `ok`/ACK 및 response status 검사보다 앞이다. 따라서 callback 도착은 확인하지만 ACK·성공 association은 보장하지 않는다. legacy `associated (aid 1)`는 ACK와 성공 status 검사 뒤 출력되므로 **그 association response의 성공 feedback은 있다.**

X/Y가 locally administered 주소라는 사실만으로 무작위 probe라고 단정할 수 없다. A의 link MAC일 수 있고, 삭제된 STA에 늦게 도착한 status, 다른 BSS/link로 전달된 callback, 재association 중 stale mapping일 수도 있다. `ap_get_link_sta()`가 현재 hapd/link의 peer mapping을 찾는 범위와 실제 callback의 link ID를 비교해야 한다. 커널은 response ACK 전에 STA를 associated로 추가할 수 있어 `iw associated: yes`와 hostapd lookup 실패는 양립한다. mapping 실패라면 hostapd의 association 완료/첫 EAPOL 시작 자체가 생략될 수 있다.

구체적으로 helper는 현재 `hapd->sta_list`의 `mld_info.links[hapd->mld_link_id].peer_addr`만 검색한다. nl80211 TX status는 cookie가 마지막 `send_frame_cookie`와 일치할 때 저장된 link ID를 넘기고 아니면 `-1`을 넘긴다. 그 뒤 `hostapd_mgmt_tx_cb()`의 link ID/BSSID 선택을 거친다. **이 경계는 다음 관측 대상이지 이번 장애에서 잘못됐다고 확인된 경로는 아니다.**

관련 자체 패치는 [999 unknown-station link ID](../../package/network/services/hostapd/patches/999-preserve-link-id-for-unknown-station.patch), [9999 expired MLD cleanup](../../package/network/services/hostapd/patches/9999-reset-expired-mld-before-link-setup.patch)다. 후자는 **기존 authorized+PMF MLD, SA Query 만료** 등의 조건에서만 partner 추가 전 정리한다. 현재 unauthorized라는 것만으로 이 경로가 발단에서 실행됐다고 알 수 없다.

## 3. 가설 순위와 다음 한 가지 관측

순위는 조사 우선순위이며 확률이나 원인 확정이 아니다. 1·2는 현재 증거로 서로 명확히 순위를 가릴 수 없다.

| 순위 / 가설 | 지지 | 반대·누락 | 다음 발생 시 한 가지 판별 관측 |
|---|---|---|---|
| 1. 공통 host→NPU TX 경로의 선택적 전달/완료 장애 | 전 대역 동시 영향, 인증 전 반복, restart 회복. `dma.c::mt76_dma_tx_queue_skb()`는 NPU active이면 일반 host TX를 `mt76_npu_dma_add_buf()`로 보냄. EAPOL/관리 frame도 이 층의 우회 조건 없음 | IRQ·현 WCID TXS/TXFREE는 살아 있음. ring/token 고갈 없음. blanket NPU 정지설은 약함. 실제 소비 index 없음 | 재접속 1회의 **host TX 증가 대비 queue 회수와 해당 WCID feedback의 1초 증분**. 준비됐는데 host tail이 계속 고정되면 경계를 좁힘. tail 진행만으로 firmware 도달을 증명하지 않음 |
| 2. MT7996 firmware 내부 data/EAPOL 처리의 partial hang | 모든 band가 공유하는 칩·firmware, MCU/관리 일부만 살아 있는 고장 가능. host ring이 비어도 내부 단계 정체 가능 | SER/reset 0, 최근 정상-status feedback, MCU disconnect result=0. firmware 전체 hang과 불일치; 내부 상태 없음 | 같은 재접속에서 **host 회수는 진행하지만 per-band TX success/해당 WCID TXS·TXFREE만 멈추는지**. 그러면 downstream 후보를 높임. NPU handoff/firmware 내부를 확정 분리하려면 별도 검증된 descriptor/RF 관측이 필요 |
| 3. hostapd STA 수명/MLD link-address mapping 또는 공통 인증 상태 오류 | MLD auth 직후 X/Y lookup 실패 반복은 직접 증거. callback을 버리면 EAPOL 시작 안 됨 | 194 보완이 이미 있음. MLD-only lookup 문제 하나로 legacy까지 설명 불가. 공통 EAPOL/rekey/config 문제도 reason 미수집 | **모든 hostapd link socket의 `all_sta` 시계열**에서 A의 `peer_addr[]`, flags/PTK state와 X/Y·callback 시각을 대조. 사전 삭제인지 다른 link/BSS인지 판별 |
| 4. 0008/0015 계열 PS/AQL TXQ 재예약 누락 | shared TXQ/AQL wake 수정 이력이 있고 0008은 공통 코드. downstream 큐가 비어도 scheduler에 backlog가 남을 수 있음 | A primary ps=0, secondary ps=1; B ps=0. 0015는 양 링크 모두 asleep일 때 shared gate, 단일 sleeping secondary만으로 못 설명. 0032/후속 rollback 재예약 보완도 존재 | **mac80211 STA `aqm` backlog/flags + `aql` pending + 같은 WCID PS/tx_prepared**를 묶은 시계열. awake인데 backlog 지속·prepared 불변이면 host scheduler 쪽을 높임 |
| 5. token/PLE/HIF 자원 고갈 또는 stale blocked 상태 | HW token 사용량·blocked flag 미노출, 장시간 누적 고장 가능 | SW 35/16384, host TX 0/1개, PLE raw 값만으로 고갈 증명 안 됨 | **정상 대비 token/queue/AQL 증가 추세**. 한계 접근·backpressure와 발단이 함께 나타나야 고갈설 강화. 숨은 HW token은 이 자료로 확정 불가 |
| 6. inactivity/SA Query/외부 해제 또는 FDB 문제 | PMF 사용, disconnect와 FDB-delete 반복 | 기본 inactivity 시간 불일치. FDB `-2` 로그는 해제 뒤 삭제와 겹치며 원인보다 결과/로그 유실 요인일 수 있음. L2 FDB만으로 locally generated EAPOL·assoc callback 실패 설명 부족 | **발단 전후 hostapd `timeout_next`, PTK state, failure counter 및 reason/event**. handshake counter 증가인지 inactivity/poll/SA Query/CLI 이벤트인지 먼저 나눔 |

mt76의 `mt7996_tx_use_mgmt()`/EAPOL 분기는 TXP flag와 link/address 선택을 바꾸며 NPU를 우회한다는 뜻이 아니다. EAPOL은 일반 data TID link steering에서 제외된다. 반면 PPE bridge fast path는 매 packet host PS gate를 거치지 않는다. [0034 TX descriptor publication](../../package/kernel/mt76/patches/0034-wifi-mt76-npu-order-tx-descriptor-publication.patch), 0035 TXS/BA activity, 0036 RED, r43 zero-budget guard도 후보 범위지만 **58시간이라는 한 표본만으로 특정 패치의 누적 누수나 timer wrap을 지목할 수 없다.** [r43 관측 한계](../mlo-r43/NPU_OBSERVABILITY.md)대로 기존 counter에서 guard hit를 복원할 수도 없다.

## 4. 다음 자동 수집 명세 — 설정 변경·재시작 없는 진단 조회

**핵심 추가 증거는 재접속 한 회의 hostapd PTK 상태/실패 counter와 같은 WCID의 TX 준비→완료 증분을 같은 clock으로 묶는 것**이다. 아래는 수집기에 넣을 명령 명세이며 이번에 설치/실행한 스크립트가 아니다. 설정 dump 대신 필요한 값만 읽고, 누락 파일·명령 실패를 0으로 대체하지 않는다.

공통 경로:

```sh
P=/sys/kernel/debug/ieee80211/phy0
D=$P/mt76
C=/var/run/hostapd
```

| 주기 | 정확한 명령/파일 | 목적 |
|---|---|---|
| 시작 1회 + incident 시작 | `uname -r`; `cat /etc/w1700k-mlo-repair`; `iw dev`; `ls -l "$C"`; `ls "$D"`; `cat /proc/sys/kernel/random/boot_id` | image/ABI·interface·control socket·파일 가용성·재부팅 구분. 개인 정보 포함 원본은 비공개 |
| 항상 streaming | `logread -f` 및 별도 `logread -f -e hostapd` | FDB spam과 별개로 hostapd 발단 보존. kernel/netifd/driver 결과도 원본 stream에 유지 |
| 정상 5초 / trigger 후 1초, 120초 | `cat /proc/uptime /proc/interrupts /proc/softirqs /proc/net/softnet_stat /proc/net/dev`; `cat "$D/token_info"`; `cat "$D/xmit-queues"`; `cat "$D/rx-queues"`; `cat "$P/queues"`; `cat "$P/aqm"`; `cat "$P/aql_pending"` | IRQ, host ring, stop reason, host backlog/AQL 증분 |
| 정상 5초 / trigger 후 1초, 120초 | 아래 AP sysfs counter loop; `iw dev phy0.0-ap0 station dump`; `iw dev ap-mld0 station dump` | BusyBox `ip -s` 실패 대체, authorization와 association 세대 |
| 정상 5초 / trigger 후 1초, 120초 | 아래 hostapd socket loop의 `all_sta`/`mib` | `flags`, `timeout_next`, `hostapdWPAPTKState`, `peer_addr[]`, `dot11RSNA4WayHandshakeFailures`, retry 설정 |
| 정상 30초 / trigger 후 1초, 처음 20초; 이후 5초 | `cat "$D/hw-queues"`; 아래 per-STA debugfs loop | PS·WCID·tx_prepared/TXS/TXFREE와 TID backlog 연결 |
| 정상 30초 / trigger 후 5초, 120초 | `cat "$D/tx_stats"`; `cat "$D/sys_recovery"`; `cat /proc/meminfo /proc/loadavg`; `cat "$D/napi_threaded"` | MIB 증분, SER/reset, 자원/부하. `napi_threaded`는 counter가 아닌 설정값 |
| 정상 60초 / trigger 직후·30초·120초 | `iw dev phy0.0-ap0 survey dump`; `iw dev ap-mld0 survey dump`; `cat /sys/kernel/debug/ppe/bind` | RF busy/noise 및 기존 PPE flow 추세. survey 지원 실패도 보존; PPE는 NPU TX counter가 아님 |

AP counter loop(각 파일명·값·실패를 함께 저장):

```sh
for I in phy0.0-ap0 ap-mld0; do
    for F in tx_packets tx_bytes tx_errors tx_dropped rx_packets rx_bytes rx_errors rx_dropped; do
        printf '%s/%s\n' "$I" "$F"
        cat "/sys/class/net/$I/statistics/$F"
    done
done
```

control socket은 이름을 미리 두 개로 제한하지 않는다. MLD link별 socket을 빠뜨리면 mapping 비교가 불가능하다. 이 tree의 생성 경로는 `/var/run/hostapd`이며 시작 시 실제 목록을 확인한다.

```sh
for S in "$C"/*; do
    [ -S "$S" ] || continue
    printf 'socket=%s\n' "${S##*/}"
    hostapd_cli -p "$C" -i "${S##*/}" all_sta
    hostapd_cli -p "$C" -i "${S##*/}" mib
done
for S in "$P"/netdev:*/stations/*; do
    [ -d "$S" ] || continue
    for F in flags aqm aql airtime num_ps_buf_frames driver_buffered_tids; do
        printf '%s/%s\n' "$S" "$F"
        cat "$S/$F"
    done
done
```

각 socket의 `hostapd_cli -p "$C" -i "$SOCKET" status`와 `status driver`도 시작·trigger·종료에 기록한다(`SOCKET`은 열거한 basename). PTK state 7=`PTKSTART`, 10=`PTKINITNEGOTIATING`, 11=`PTKINITDONE`이다. hostapd link ID와 driver band 번호를 같다고 가정하지 않는다. 이 build는 `CONFIG_CTRL_IFACE_MIB=y`지만 `CONFIG_NO_DUMP_STATE=y`이므로 `sta <MAC> eapol` 대신 `all_sta`를 사용한다.

**이미 활성화된 udebug ring이 있을 때만**, trigger·10초 뒤·30초 뒤에 최근 30초를 추가 보존한다. `udebug-cli list`로 이름/존재를 확인하고 없으면 SKIP 처리한다. 기본 hostapd udebug는 disabled이며 자동 활성화하지 않는다.

```sh
udebug-cli list
udebug-cli -i '*:wpa_log' -d 30 -t logdump
udebug-cli -i '*:wpa_nl_rx' -i '*:wpa_nl_tx' -i '*:wpa_nl_ctrl' -d 30 -o "$PRIVATE_FILE" snapshot
```

`PRIVATE_FILE`은 수집기가 만든 비공개·매번 고유한 출력 파일이다. 원시 netlink에는 키/식별자가 포함될 수 있으므로 공개하지 않고 control-port TX/RX, ACK, reason, frame type, cookie/link ID와 시각만 추출한다. `-e`, `set`, `set_flag`, `reset`은 실행하지 않는다. 이 build는 mac80211 control-port/TX-status capability와 hostapd `control_port_ap=1` 경로가 있어, 가능하면 이 기존 netlink 기록이 AP tcpdump보다 분별력이 높다.

운영 조건:

- 각 조회의 시작/종료에 `date -u '+%Y-%m-%dT%H:%M:%SZ'`와 `/proc/uptime`을 기록한다. 비동시 읽기·초과 소요시간·exit status를 보존하고 수집 loop 중첩을 막는다. 지원되는 `timeout`으로 느린 개별 명령을 제한한다. hostapd_cli는 exit 0이어도 `FAIL`/`UNKNOWN COMMAND`일 수 있어 응답 본문까지 검사한다.
- trigger는 `local deauth request` 또는 `handle_assoc_cb ... not found`가 10초 안에 3회, 또는 양 AP의 관측 STA가 10초 이상 unauthorized인 경우로 시작한다. 정상 자료도 최소 10분 유지한다. trigger가 참 원인을 뜻하지 않으며 이미 발생한 ring 유실은 되살릴 수 없다.
- streaming/정상/incident 자료는 수집기가 **별도 상한을 둔 RAM ring**에 저장한다(예: 총 32 MiB). incident 발생 시 직전 ring을 보존하고 반복 trigger로 덮어쓰지 않는다. flash 지속 쓰기·전체 설정/키 dump는 피하고, raw log·MAC·peer mapping·PPE tuple은 비공개로 둔다. 공유 시 동일 단말/association의 일관된 가명만 남긴다.
- `hw-queues` getter는 queue-query selector 레지스터를 쓴다. recovery/flush는 아니지만 엄밀한 MMIO 무쓰기 관측은 아니다. `tx_stats` getter는 clear-on-read MIB를 driver 누적치로 회수하므로 **한 collector에서 순차 조회**한다. raw register reader와 병행하지 않는다. `sys_recovery`는 `cat`만 한다.
- 이 버전에 일반 `/mt76/wfdma`, `/mt76/irq_stats`, `/sys/kernel/debug/npu` runtime counter는 확인되지 않았다. `rx-queues`는 대체 WFDMA counter가 아니다. 존재하지 않는 파일을 정상 0으로 기록하거나, STOP/mailbox query·`devmem`·`regidx/regval` 임의 탐색으로 관측을 보충하지 않는다.
- EAPOL의 host 관측은 평상시 먼저 가시성을 확인한 경우에 한해 `tcpdump -p -ni phy0.0-ap0 -e -tt -l 'ether proto 0x888e'`와 `ap-mld0`의 동일 명령을 별도 bounded stream으로 추가한다. ACK/무선 송신 성공의 증거는 아니며, nl80211 control-port 경로는 AP netdev capture에서 빠질 수 있어 **안 보인다는 이유로 미전송 판정 금지**다. packet payload/키를 출력하는 `-X/-XX`는 사용하지 않는다.
- hostapd 상세 reason/TX-status가 현재 log level에서 빠지면 `all_sta/mib`만으로 ACK 여부나 SA Query를 완전히 복원할 수 없다. 추가 netlink/firmware 계측과 별도 수신기의 RF capture는 그 다음 증거 단계다. 현재 AP에 monitor VIF를 추가하거나 channel/PS/offload/debug level을 바꾸는 자동 조치는 포함하지 않는다.

검증 범위: 정적 소스 대조·snapshot 산술/문구 검토만 수행했다. 다음 capture 명령은 r44의 모든 runtime socket/파일에서 실행 검증한 것이 아니다. source 수정이나 firmware 원인 해결을 주장하지 않는다.
