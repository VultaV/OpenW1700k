# r36 — NPU TX descriptor 게시 순서 수정·펌웨어 경계 분석

r35의 호스트 NPU 송신 경로에서 확인한 메모리 게시 순서 누락을 수정한 **실험 버전**입니다. **공유기에 접근·설치·재부팅하거나 추가 무선 시험을 하지 않았습니다.** Air 절전 복귀의 간헐 멈춤이 해결됐다는 의미는 아닙니다.

## r35 대비 개선

- **TXWI·주소를 DONE보다 먼저 게시:** NPU는 host ring의 DONE을 직접 polling합니다. 기존의 뒤쪽 CPU-index 갱신 barrier로 앞선 ownership 공개를 보호할 수 없어, 공유 함수 `mt76_npu_dma_add_buf()`에 `dma_wmb()`와 `WRITE_ONCE()`를 적용했습니다. descriptor 레이아웃·내용·ring accounting·기존 가속 경로는 유지합니다.
- **실제 컴파일 결과 확인:** ARM64 `npu.o`에서 TXWI 복사 → 주소 store → `dmb oshst` → DONE 포함 control store 순서를 확인했습니다. r35 object에는 해당 barrier가 없습니다. vendor consumer 310개 명령 행도 현재 blob과 바이트 대조했습니다.
- **NPU 바이너리의 별도 오류 기록:** 출력 ring 여유가 정확히 7개일 때 budget0이 전달되고, 성공 처리 뒤 `0xffffffff`로 되감겨 정상 128개 제한을 우회하는 경계를 확인했습니다. stop/timeout의 계속 진행 분기, 독립 packet-buffer 반환 경로와 reset 무제한 대기도 정리했습니다. **NPU 바이너리는 변경하지 않았습니다.**
- **기존 Air 기록 재분석:** 상세 상태 수집의 약5초 공백과 순차 읽기 시간을 반영했습니다. 기존 기록으로 전역 NPU 정지와 단일 peer의 ACK/스케줄 정체를 구분할 수 없음을 명확히 했습니다.

## 검증

9개 make 단계를 모두 실행해 종료코드 0으로 완료했습니다. 반복 포함 경고 **385줄·정규화 메시지 148종**이 있습니다. r35와 공통148종, 신규0종, 이번에 미관측1종입니다. 미관측 경고를 해결된 것으로 세지 않으며 모든 경고가 무해하다는 판정도 아닙니다. 미사용 의존성14종과 빈 kmod28개의 설정·실제 이미지 설치 여부는 `BUILD_WARNINGS.json`에 있습니다.

| 검사 | 통과 | 실패 | 경고 | 생략 |
|---|---:|---:|---:|---:|
| 새 NPU TX 계약 | 8사례 | 0 | 0 | 0 |
| 기존 NPU RX | 3그룹 | 0 | 0 | 0 |
| 링크 전환 / forward path | 24 / 92 | 0 | 0 | 0 |
| 링크 수명 / MLO PS | 631 / 99 | 0 | 0 | 0 |
| NPU watchdog | 90 | 0 | 0 | 0 |
| TTL 구조 / 추출 C 가드 | 12 / 2,091 | 0 | 0 | 0 |
| conntrack / PPE / FDB | 7 / 11 / 1,026 | 0 | 0 | 0 |
| 이미지의 업데이트 UI | 9 | 0 | 0 | 0 |

각 검사 범위 내 통과율은 100%입니다. 그룹과 assertion 수를 하나의 총수로 합산하지 않습니다. 실제 prepared 함수를 ASan/UBSan으로 실행하되 kernel·DMA·RCU·MCU·하드웨어는 대체 환경입니다. 실기기 안정성·약한 메모리 순서의 발생률·부팅 통과율이 아닙니다.

수정 전 TX 8개와 barrier 제거 TX 8개가 의도한 계약 실패를 재현했습니다. RX barrier 제거도 거부했습니다. 실제 로그의 계약 실패 문구를 확인하고 sanitizer 오류가 없는지 별도로 검사했으며, 예상 실패를 수정본 실패로 합산하지 않습니다.

firmware budget 모델은 원본 **1,534 통과 / 2 기대된 실패**이며 두 ring의 free=7에서 실패했습니다. zero-budget skip 모델은 **1,536 통과 / 0 실패**입니다. 선택된 1,153행·표준 branch offset26개와 jump table3개를 검사했습니다. 별도 completion pool 분석은 1,356행·모델5사례 및 변조 입력2개 거부를 기록했습니다. 이는 제한된 byte/산술 검사이며 실제 firmware 수정·전체 제어 흐름·도달 가능한 교착·Air 원인 증명이 아닙니다.

이미지의 FIT·UBI2 메타데이터, 206개 패키지, 64개 kmod 의존성, 74개 모듈 vermagic을 검사했습니다. **커널 payload와 73개 모듈은 r35와 바이트 동일하고 변경 모듈은 `mt76.ko` 하나입니다.** 해당 모듈은 이번 빌드 package payload와 일치합니다. mt7996e, NPU 모듈, firmware11개 및 wpad/LuCI338파일은 동일합니다. Tailscale 패키지·서비스·상태 보존 경로를 확인했고 개인 상태 파일은 이미지에 없습니다.

## 남은 문제와 공개 패치

[전체 후속 검토](https://github.com/VultaV/OpenW1700k/blob/mlo-r36-20260926/docs/mlo-r36/REVIEW.md)에 firmware budget·stop·pool 경계와 기존 권한/설정 UI, 실패한 activation rollback, RRO/PPE 삭제 오류, PPE binding 무효화의 미해결 범위를 기록했습니다. 가속 bulk traffic은 호스트의 매 패킷 송신을 우회하므로 이번 barrier 수정만으로 Air의 간헐 멈춤을 설명하지 않습니다. **그 원인·해결은 미확정입니다.**

[9월26일 upstream 조사](https://github.com/VultaV/OpenW1700k/blob/mlo-r36-20260926/docs/mlo-r33/FULL_REVIEW_20260926.md)의 일반 UBI2는 `r36602-54e453b074`·kernel6.18.52이며 직전 일반 빌드와 firmware12개가 동일했습니다. 995/996의 L2 TTL·교차 ingress 보호는 기존 KEEP_TTL·소유권·FDB 수정 전체의 대체가 아닙니다. 공식 NPU watchdog 백포트는 r34부터 유지합니다. FDK·Clanker는 재구현이며 현재 vendor blob과 동일하지 않습니다. 일부 포럼 본문은 접근 실패로 미확인입니다. r36은 최신 upstream 전체 교체가 아닙니다.
