# r65 — MLO DFS 대피 채널 선택 개선 (실험 버전)

**설치·실기기 검증 완료. 원인 확정된 DFS 전대역 장애는 개선됐습니다. 초기 TCP 정지와 일부 흐름의 속도 저하는 아직 원인 미확정이므로 전체 MLO 안정성이 해결된 버전으로 표시하지 않습니다.**

## 원인과 수정

- r62의 MT7996 드라이버는 공유 `ieee80211_hw`에 레이더 채널 컨텍스트를 NULL로 전달해 2.4/6GHz까지 잘못 감지시켰습니다. r64의 해당 라디오 범위 제한 및 운용 채널 TX 재개 수정을 유지합니다.
- r64에서 남은 160MHz 장애는 hostapd가 즉시 쓸 수 있는 80MHz보다 CAC가 필요한 160MHz를 먼저 선택해 MLD를 재시작한 경로였습니다. r65는 MLO에서 즉시 사용 가능한 좁은 채널을 먼저 선택해 링크별 CSA로 대피합니다.
- 기존 DFS/NOP 가용성 검사를 사용하며, 즉시 쓸 채널이 없으면 기존 CAC 절차를 따릅니다. ETSI uniform spreading과 일반 AP 경로는 유지합니다. 레이더 대피 시 채널 폭이 80/40MHz로 낮아질 수 있습니다.

## 실기기 결과

Mac en0에 시험 트래픽을 고정했습니다. Linux iperf 서버는 LAN2 2.5Gbps, 유선 관리 en10은 LAN4 1Gbps입니다. 고정된 공유기 근처 위치에서 자동 출력으로 측정했습니다.

각 방향 90초, TCP 4 streams:

| 조합 | 다운로드 Mbps | 업로드 Mbps | 0Mbps 구간 내려/올리기 |
|---|---:|---:|---:|
| 2.4+5GHz | 1918 | 1814 | 0 / 0 |
| 2.4+6GHz | 1953 | 1835 | 0 / 0 |
| 2.4+5+6GHz | 1895 | 1829 | 0 / 0 |
| 5+6GHz | 1958 | 1833 | 0 / 0 |

- 8회 측정의 Wi-Fi ping3517회 모두 응답. 2.4+5GHz에서 중복 ICMP 응답1개는 별도 기록했습니다. 링크 마스크가 여러 링크의 동시 데이터 합산을 증명하지는 않습니다.
- **DFS160:** r64의 연속27초 0Mbps 및 ping23.8% 손실 → r65에서 **0Mbps구간0, ping441/441, AP 재시작·beacon 오류·CAC 재시작 없음**. 전송이 진행된 뒤 실제 새 레이더 이벤트와 160→80MHz CSA를 확인했습니다. 단, 순간 최저124.6Mbps, 500Mbps 미만12개 구간이 있었고 마지막30초 평균1954.4Mbps로 회복했습니다.
- 첫 DFS 시도는 전송 전에 레이더가 먼저 발생해 연속성 판정에서 제외했습니다. 사용 금지 시간30분을 지킨 후 재시험했습니다.
- 두 링크 PS=1 상태로2분 유휴 후 내려받기1957.5Mbps(120초), 올리기1793.5Mbps(60초), 0Mbps없음. 전체 macOS 잠자기 시험은 아닙니다.
- 원래 2.4GHz AP(20MHz)는143.4Mbps(30초), 0Mbps없음. DNS3개 도메인·인증서 검증 HTTPS·외부 ping20/20통과. 최종 MLO에서도 DNS·HTTPS·외부 ping20/20통과.
- 허용된 설치·재부팅 구간을 제외한 유선 링크/공유기 응답 **4419회**, 유선 WAN **885회**에서 실패0. 원래 설정 해시 일치, UCI 변경 없음, Mac MLO두 링크 복귀, SSH/Tailscale 정상, 임시 복원 가드 종료.

## 남은 TCP 관찰 — 미해결

- 2.4GHz SSID에서 MLO로 복귀한 뒤 첫300초 다운로드의4~9초 구간에 0Mbps5개가 있었습니다(평균1878.0Mbps, 동시 ping1472/1472). 해당 초기 구간은 큐 수집 시작 전이라 원인을 단정할 수 없습니다.
- 같은 연결에서 재측정한300초 다운로드1953.3Mbps, 업로드1724.3Mbps는 0Mbps와 ping손실이 없었습니다.
- 재연결3회 다운로드는1934.9 /1906.4 /385.1Mbps였고 0Mbps는 없었습니다. 마지막 저속 흐름은 PHY2401Mbps, 6GHz주 링크, TCP재전송0이었습니다. 무선 연결을 바꾸지 않고 새 흐름을 시작하자1933.8Mbps로 복귀했으며, 추가 흐름3회도1898.1 /1917.6 /1955.0Mbps였습니다. 원인은 미확정이며 근거 없는 펌웨어 수정을 추가하지 않았습니다.

## 빌드·설치 기록

- 소스 `447f3823006507b792e518764230ce931a4e6381`, 빌드 태그 `mlo-r65-20261105`.

- 이미지 SHA256: `f96a2516380a983e63646a3d0c05d76209d27299b20ba360817a858d9debcdff`.
- 네이티브 보드/이미지 검사를 통과하고 설정 유지 방식으로 설치했습니다. 설정·SSH키·Tailscale상태를 보존했고 설치된 wpad/모듈/NPU해시를 대조했습니다. 비공개 백업·계정 상태·단말 식별자는 공개하지 않습니다.

## 제한

실험용 prerelease입니다. 야간 장기 안정성, 전체 OS잠자기, 실제 약전계의5/6→2.4GHz전환은 검증하지 않았습니다. NPU0.8은 시험 펌웨어이며 구형 바이트쌍 전용 TX-budget guard는 적용되지 않습니다. FIT해시 검증은 신뢰된 서명키 검증을 뜻하지 않습니다. 설치 중 유선·Tailscale은 일시 중단됩니다.
