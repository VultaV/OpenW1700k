# r41 — 링크 활성화 실패 후 멈춘 TXQ 재등록

**실험용 prerelease. 빌드·이미지·설치·부팅 및 Mac 비교 시험 완료. 새 연결 초반 저하는 남아 있습니다.**

새 MLO 링크 활성화 중 드라이버 오류가 발생하면, 임시 링크 마스크 때문에 스케줄 목록에서 빠진 공유 송신 큐가 기존 마스크 복원 뒤에도 멈춰 있을 수 있습니다. r41은 mac80211의 실패 경로에서 마스크 복원과 링크 정리가 끝난 뒤, 데이터가 남은 TXQ를 다시 등록하고 드라이버에 알립니다. 원래 오류 반환값과 PS·AQL 검사, 재설정 중 wake 보류 동작은 유지합니다.

이 수정은 조건부 실패 복구입니다. 최근 Mac 새 연결 초반 저하나 기존 Air 절전 복귀 멈춤을 해결했다고 판정하지 않습니다. r40에서 도입한 RED 실험의 효과도 이 변경으로 입증되지 않습니다.

## 완료한 오프라인 검사

- 실제 mac80211 core 함수와 mt7996/mt76 함수를 추출한 회귀 검사: 원본 **39개 assertion 충족**, 후보 **39개 assertion 충족**, 양쪽 예상 밖 실패 **0개**. 기존 24개 검사에 core 경로 15개를 추가했습니다.
- 원본 검사는 오류 후 마스크 복원과 AQL 반환에도 backlog **10개가 미등록 상태로 남는 정확한 음성 대조**를 포함합니다. 원본 제품 동작이 정상이라는 뜻이 아닙니다. 후보에서는 같은 10개를 실제 추출 scheduler가 처리합니다.
- active-mask filtering, 오류값·기존 링크·PS 상태 보존, 성공·early exit, null/empty/fragment TXQ, 재설정 중 DIRTY 처리와 잠금 조건을 확인했습니다. ASan·UBSan 정상입니다.
- 활성 목록·잠금·RCU·할당·hash/debugfs는 host fixture입니다. 실제 동시 실행, RCU grace period, DMA 수명이나 장비 성능은 이 검사 범위가 아닙니다.

공식 Linux [`fd179f8a05be`의 활성화 함수](https://github.com/torvalds/linux/blob/fd179f8a05be3ccae366b9b96e176b51fbe54aab/net/mac80211/sta_info.c)는 로컬 원본과 동일했습니다. 해당 revision의 함수 비교이며 모든 상위 대기 패치에 대한 결론은 아닙니다.

## 빌드 검증

9단계 빌드와 13개 소스 검사, 설치 이미지 UI 9개 검사가 통과했습니다. 실제 prepared 소스 두 변형을 원본+패치와 대조하고 정확한 역방향 복원도 확인했습니다.

mac80211 package release는 **2 → 3**, 변경 모듈은 **`mac80211.ko` 하나**입니다. 나머지 73개 모듈, 커널 payload, 11개 펌웨어와 338개 wpad/LuCI 파일은 r40과 같습니다. kernel release는 `6.18.44-w1700k-mlo-r32`이며 kernel package ABI도 r40과 같습니다.

빌드 경고는 **383회·147종**이며 r40과 같은 정규화 문구입니다. 새 문구와 수정 파일 직접 경고는 0개지만 기존 경고가 무해함을 입증한 것은 아닙니다. 경고 원문 분류는 BUILD_WARNINGS.json에 기록했습니다.

펌웨어 크기: **30,290,792 bytes**. SHA256: `092788281aae270fb8dcd5e85d8a4ed16ad433bdfc75105028bdc29d9b0eca6f`.

## 설치·실기기 검증

설치 후 24개 검사가 통과했고 설정 34개·Tailscale·모듈 74개 해시를 확인했습니다. Mac 60초 MLO 시험은 새 연결 평균 1730.97Mbps / 최저 70.49Mbps, 안정 후 평균 1923.28Mbps / 최저 1774.38Mbps였고 두 회차 모두 0Mbps 구간은 없었습니다. 새 연결 첫 5초의 저하는 남아 있습니다. 유선 확인 154회 정상, 시험 후 핫스팟 복원 완료입니다.

한 차례 순차 비교이며 r41의 성능 개선이나 Air 멈춤 해결 증거로 해석하지 않습니다. 실패 활성화 분기는 장비에서 강제 주입하지 않았습니다. BUILD_RESULT.json은 설치 전 빌드 시점 기록이며, 추가 검증은 [설치·Mac 시험 결과](https://github.com/VultaV/OpenW1700k/releases/download/mlo-r41-20260927/DEVICE_TESTS_20260927.md)에 분리했습니다.

## 연결 후 스캔 시점의 추가 비교

같은 Mac에서 iperf를 더 일찍 시작하자 MLO와 6GHz 단일 링크 모두 초반 약 1.9Gbps 전송 후, 연결 나이 약 22초에 첫 500Mbps 미만 구간이 나타났습니다. macOS의 연결 후 20초 BEST CONNECTED 스캔 요청·절전 상태·재전송 증가가 함께 관측됐습니다. BA 준비는 전송 전에 끝나 있었으며, 이번 현상을 MLO 두 링크만의 문제로 한정할 수 없습니다. 공통 NPU/PPE·Wi-Fi 펌웨어 경로의 영향과 원래 Air 절전 복귀 멈춤은 미확정입니다.

40초 평균/최저는 MLO 1241/66Mbps, 단일 6GHz 1383/133Mbps입니다. 두 회차 모두 0Mbps 구간은 없었고, 일시 저하가 포함된 순차 시험이므로 모드별 우열이나 수정 효과로 해석하지 않습니다. 유선 확인과 설정·진단 옵션·핫스팟 복원을 검증했습니다. 신규 제품 수정·펌웨어·태그 변경은 없습니다. [상세 비교 및 관측 한계](https://github.com/VultaV/OpenW1700k/releases/download/mlo-r41-20260927/ASSOCIATION_COMPARISON_20260927.md).


## 같은 설정 전송률에서 가속 경로를 제외한 비교

새 MLO 연결에서 150Mbps × 4, 합계 목표 600Mbps로 PPE 가속과 시험 데이터만의 가속 우회를 비교했습니다. 두 경로 모두 연결 후 약 20.3초 BEST CONNECTED 스캔 요청에 이어 약 22초에 급락했습니다. 40초 평균/최저는 가속 **599.99/69.78Mbps**, 우회 **599.97/46.21Mbps**였으며 500Mbps 미만 표본은 13/14개, 0 표본은 모두 없었습니다. 설정 전송률은 순간 상한이 아니며 회복 후 catch-up burst가 있어 실제 순간 입력량까지 동일한 시험은 아닙니다.

우회 경로의 네 데이터 tuple을 6개 시점에서 검사해 OFFLOAD/HW_OFFLOAD·양방향 PPE BND 부재를 확인했고, 임시 규칙 복원과 원본 규칙 해시 일치도 검증했습니다. 유선 HTTP 확인 109회는 모두 정상이었습니다. 따라서 이번 Mac 초기 저하에 시험 데이터의 PPE 가속은 필수 조건이 아니었습니다. **전역 NPU·공통 Wi-Fi 경로와 원래 Air 절전 복귀 문제는 배제하지 않습니다.** API 호출은 RF 체류 시간이 아니며 PS 로그 누락도 남습니다. 신규 제품 소스·펌웨어·태그 변경 없이 진단 문서만 추가했습니다. [상세 비교·관측 한계](https://github.com/VultaV/OpenW1700k/blob/codex/mlo-r30-bridge-offload/docs/mlo-r41/scan-path-20260927/SCAN_PATH_COMPARISON_20260927.md).

## Neighbor Report 구성 후 초기 전송 관찰

**NR 두 항목의 설정·조회는 확인했지만 Mac의 실제 요청·응답 수신·사용은 미검증입니다.** `CONFIG_WPA_MSG_MIN_PRIORITY=3`으로 DEBUG/MSGDUMP가 빌드에서 제외돼, 런타임 MSGDUMP 설정만으로 프레임 관측 공백을 채울 수 없었습니다.

동일한 TCP 목표 600Mbps의 새 MLO 연결에서 평균/최저 **600.03/67.43Mbps**, 500Mbps 미만 13개·0Mbps 0개 표본을 기록했습니다. 기준 회차와 같이 연결 나이 약 22초에 저하됐고, native background 요청은 33회·97채널로 순서가 같았습니다. NR 전달 효과나 무효를 확정하는 결과는 아닙니다. 추가 로깅 부하·PS 기록 누락·서로 다른 연결이라는 한계가 남습니다.

NR 및 로그 설정·원래 네 설정 파일·bridge 규칙 복원을 확인했고, NR 제어기 유선 관측 131회와 전송 제어기 56회가 정상이었습니다. 신규 제품 소스·펌웨어·태그 변경은 없으며 원래 Air 절전 복귀 문제도 미해결입니다. [비교 수치·관측 한계·복원 기록](https://github.com/VultaV/OpenW1700k/blob/codex/mlo-r30-bridge-offload/docs/mlo-r41/neighbor-report-20260927/NR_CONFIG_COMPARISON_20260927.md).

## 기존 커널의 관리 통신 관측 경로 확인

펌웨어 변경 없이 기존 nlmon과 tcpdump로 완전한 nl80211 family·인터페이스 조회 왕복을 확인했습니다. 다만 128개 패킷 상한에 도달해 실제 기록은 5.423481초였고, 잘린 3개는 통째로 제외했습니다. **예정한 20초 전체 캡처는 실패했으며 NR 전달·ACK·Mac의 사용은 아직 미검증입니다.** 임시 모듈·인터페이스 제거, 원본 설정·nft·부팅·taint 유지와 유선 관측 8회 정상을 확인했습니다. 첫 도구 실행 실패와 수동 복원도 기록했습니다. [관측 범위·한계와 검증 기록](https://github.com/VultaV/OpenW1700k/blob/codex/mlo-r30-bridge-offload/docs/mlo-r41/nlmon-observer-20260927/NLMON_OBSERVER_20260927.md).

## 실제 Neighbor Report 응답 확인과 복원 오류

Mac의 Neighbor Report 요청→응답→동일 프레임 ACK 1회와 응답 안의 두 실제 AP 보고서를 확인했습니다. 그 뒤에도 연결 후 약 20.3초의 background scan 요청과 초기 저하가 남았습니다. 같은 목표 600Mbps 시험은 평균/최저 **600.02/62.86Mbps**, 500Mbps 미만 14/40개 표본·0Mbps 0개였고 스캔 요청 목록은 기존 두 회차와 같은 33회·97채널이었습니다. **정보 수신은 확인했지만 채택·스캔 억제 효과는 입증되지 않았습니다.** 관측한 1126개 패킷의 잘림·kernel drop은 0개였으며, 원시 패킷은 공개하지 않습니다.

시험 도구의 AP 대기가 60초 DFS CAC보다 짧던 문제를 수정했습니다. 재시험 후 자동 원복에서는 별도로 5GHz 채널 설정 단계 실패(HT_SCAN→DISABLED)가 발생했습니다. radio1 재생성 후 두 AP·원본 설정 34개·정적 규칙·진단 옵션을 검증하고 가속과 핫스팟을 복구했습니다. NR 제어기 유선 확인 212회와 수동 복구 63회는 정상이었으며, 자동 원복 성공으로 표시하지 않습니다. 신규 제품 소스·펌웨어·태그 변경은 없고 원래 Air 문제도 미해결입니다. [실제 교환·비교·복구 상세](https://github.com/VultaV/OpenW1700k/blob/codex/mlo-r30-bridge-offload/docs/mlo-r41/neighbor-exchange-20260927/NR_EXCHANGE_REPORT_20260927.md).

## AP 재생성의 채널 응답 추적

실시간 nlmon 필터와 대상 Linux errno 해석을 바로잡고, 읽기 전용 요청·응답 1쌍으로 관측 경로를 확인했습니다. 원래 설정의 정상 재생성과 1초 대기 변형에서 180/190개 패킷을 드롭 없이 기록했으며 두 대역의 채널 설정·AP 시작은 성공했습니다. 5GHz STOP_AP→SET_WIPHY 요청 간격은 **1.568108/1.932121초**로 모두 2초 미만입니다. **앞선 채널 설정 실패와 DFS 만료의 인과관계는 여전히 미확정**입니다.

마지막 1.5초 대기 변형은 장치의 소수 초 sleep 미지원으로 중단되어 비교에서 제외했습니다. 자동 복원 실패를 보존하고 수동 AP 시작·정상 DFS CAC 이후 원래 가속과 설정 34개를 복원했습니다. 최종 두 AP와 유선 링크, 진단 옵션·임시 모듈 정리를 확인했으며 제어 27회·복구 56회의 유선 관측은 모두 정상이었습니다. r41 제품 소스·펌웨어·태그 변경은 없고 Mac 초기 저하와 원래 Air 문제도 해결 판정하지 않습니다. [회차별 근거·복구·기존 패치 확인](https://github.com/VultaV/OpenW1700k/blob/codex/mlo-r30-bridge-offload/docs/mlo-r41/channel-restore-20260927/CHANNEL_RESTORE_20260927.md).
