# MLO r33: r32 브리지 가속 호환성 수정

Gemtek W1700K UBI2용 **시험 릴리스**입니다. r32에 포함된 가속 패키지가 r30 커널만 허용해 부팅 후 가속이 꺼지던 문제를 수정했습니다. r33은 **`6.18.44-w1700k-mlo-r32` 커널·모듈 ABI를 유지**합니다.

## 개선 사항

- `bridge-flow-offload 1.0-r2 → 1.0-r3`: TTL 실측을 통과한 r30·r32 커널을 정확히 허용합니다. 다른 커널은 계속 거부합니다.
- 직접 실행·fw4 포함·네트워크 및 인터페이스 hotplug가 사용하는 공통 검사를 수정했습니다. 새 설치의 가속 기본값은 비활성화이며 포트·격리·VLAN·정책 검사를 유지합니다.
- 이미지 검증 시 이미지 안의 실제 가속 스크립트를 해당 이미지의 커널 값으로 실행합니다. 커널 버전 증가 때 같은 호환성 오류가 재발하면 검증이 실패합니다.
- r32의 단말 제거 시 이전 브리지 흐름 정리와 PPE 슬롯 소유권 보호를 유지합니다. NPU·무선 펌웨어와 wpad/LuCI는 변경하지 않았습니다.

## 검증과 설치 상태

- 규칙 생성기: **21 통과 / 0 실패 / 0 경고 / 0 생략, 통과율 100%**. 수정 전 소스에서 네 호출 경로의 r32 거부를 재현했습니다.
- 전체 빌드 9단계가 통과했습니다. 이미지의 커널·모듈 74개·펌웨어 11개는 r32와 바이트 단위로 동일합니다. 패키지 206개를 유지하며 버전 변경은 가속 패키지 하나입니다. FIT 해시·UBI2 보드 정보·개인 Tailscale 상태 미포함을 확인했습니다.
- **실기기 시험은 r32 설치 이미지에 `1.0-r3` 패키지만 적용한 구성**입니다. r33 전체 이미지를 다시 설치·부팅한 결과는 아닙니다.
- 해당 구성에서 설치 후 검사 **24 통과 / 0 실패 / 0 경고 / 0 생략**이며 기존 설정·Tailscale·유선 연결과 가속 복원을 확인했습니다. APK 설치 중 xattr 보존 경고 7개가 있었고 설치 파일 내용·설정 해시를 검증했습니다. 생성된 기본 설정 후보는 따로 보관했습니다.
- r32 IPv4 역방향 TCP 100Mbps·8초씩 가속 없음/소프트웨어/하드웨어 비교: **42 통과 / 0 실패**. 수신 패킷 208,614개 모두 TTL 64, 커널 캡처 드롭 0개입니다. 전속도·IPv6 TTL 검증은 아닙니다.
- Mac 재연결 1회: r30에서는 단말 부재 15초 뒤에도 시험 흐름의 PPE 항목 8개가 남았습니다. r32에서는 첫 관측(부재 확인 약 0.149초 뒤)과 15초 뒤 모두 0개였고, 재연결 후 8개가 다시 등록됐습니다. 유선 관측 107회가 모두 통과했고 시험 뒤 Mac 원래 Wi-Fi를 복원했습니다.

재연결 후 후반 33개 1초 구간의 TCP 처리량은 약 1,738Mbps였고 전송량 0인 구간은 없었습니다. 의도적으로 Wi-Fi를 끈 구간은 제외한 수치이며, r30 대비 통제된 속도 개선 측정으로 해석하지 않습니다.

## 추가 실기기 기록 — 2026-09-24

r32 커널에 `bridge-flow-offload 1.0-r3`를 적용한 상태에서 Mac MLO 업로드·다운로드를 각각 5분간 측정했습니다. 각 회차는 새 연결 후 60초 대기했으며, 동일 연결에서 펌웨어를 바꾼 속도 비교는 아닙니다.

| 방향 | 실제 수신 평균 | 1초 수신 최저 | 0 전송 구간 | 전체 CPU 사용률 |
| --- | ---: | ---: | ---: | ---: |
| 업로드 | 1,772Mbps | 1,380Mbps | 0/300 | 5.02% |
| 다운로드 | 1,880Mbps | 1,395Mbps | 0/300 | 6.23% |

업로드의 1초 값은 서버 수신 보고서의 반올림된 값이며 다운로드는 Mac 수신 JSON입니다. 두 회차 모두 트래픽 중 스냅샷에서 4개 흐름·PPE 양방향 8개가 등록됐습니다. 유선 확인 **812/812 통과**, 시험 뒤 설정·부팅 상태와 Mac의 원래 Wi-Fi를 확인했습니다. 업로드에서 NPU 대기 주소 표본이 1개 있었으나 지속 정지나 속도 저하 원인으로 확인되지 않았습니다.

별도 180초 재연결 시험에서는 Mac 부재 중 Air를 한 번 재연결했지만 **WCID가 바뀌지 않아 변경 WCID 시험은 미완료**입니다. Mac 부재 확인 약 0.143초 뒤와 15.599초 뒤의 이전 PPE 항목은 모두 0개였습니다. 재연결 직후 가속 확인은 4개 중 1개만 통과했고, 시작 후 135초 이후 스냅샷에서는 4개 모두 복구됐습니다. 흐름별 스냅샷 검사 총 **17 통과 / 3 실패 / 20건, 통과율 85%**이며 실패 3건을 기록에 그대로 남겼습니다. 이는 즉시 복구 검사 결과이며 영구 가속 실패를 뜻하지는 않습니다.

재연결 확인 후 96개 1초 수신 구간에는 0 전송이 없었지만 500Mbps 미만 구간이 14개 있었습니다. 마지막 30초는 평균 1,933Mbps였으나, 중간 저하 원인은 아직 확인되지 않았습니다. 해당 시각의 조회 로그에서 Mac 스캔 요청을 찾지 못했고 이것만으로 모든 무선 스캔을 배제하지 않습니다. 유선 확인은 **163/163 통과**했습니다.

Air는 이 재연결 시도에서 6GHz 단일 링크였고 저장된 연결 요청에는 EHT 기능 정보가 있지만 Multi-Link 요소가 없었습니다. 이것만으로 AP 광고·단말 캐시·단말 동작 중 어느 쪽이 원인인지 판정할 수 없습니다. 이 회차는 Air iPerf 시험이 아닙니다.

첨부 `R32_SUSTAINED_VALIDATION.json`, `R32_WCID_ATTEMPT.json`에 식별자를 제거한 수치와 미확인 범위를 보존했습니다. 기존 빌드 태그·펌웨어는 변경하지 않았습니다.

### 재연결 직후 저하 추가 진단

Air를 건드리지 않은 별도 Mac 재연결 시험에서 1초 간격으로 210개 표본을 수집했습니다. 재연결 확인 뒤 87개 표본 모두 4개 흐름·PPE 양방향 8개가 등록됐지만, 실제 수신에는 500Mbps 미만 구간 16개가 있었습니다. 저하 구간에 가장 가까운 표본의 전체 CPU 사용률은 3.27~6.53%, 보고된 PHY 속도는 2,401.9Mbps였습니다. **이 저하는 가속 항목 누락이나 CPU 포화만으로 설명되지 않습니다.** 유선 확인 201/201 통과, 설정·부팅·Mac 원래 Wi-Fi 복원을 확인했습니다. 기록 자체의 부하가 있으므로 정식 성능 비교로 사용하지 않습니다.

이어 새 Mac 연결 직후 대기 없이 2분간 측정하며 `airportd` 스캔 로그를 실시간 수집했습니다. 시험 시작 12.36초 뒤 `BEST CONNECTED SCAN` 요청과 12.39~23.98초 사이 라이브 스캔 요청 33개를 확인했습니다. 수신 저하는 약 14~29초에 나타났고, 저하 시점의 가속 스냅샷은 4개 흐름·8개 PPE 항목을 유지했습니다. 시작 60초 이후 60개 구간은 평균 1,871Mbps, 최저 1,822Mbps, 0 전송 구간 없이 끝났습니다. 유선 확인 149/149도 통과했습니다.

스캔과 저하의 시간적 중첩은 **이번 Mac의 연결 직후 저하에 대한 유력한 단서**입니다. 스캔을 통제한 인과 실험은 아니며 Air의 과거 멈춤이나 이전 모든 Mac 저하의 원인으로 확대하지 않습니다. 과거 저장 로그에 스캔 요청이 없었다는 사실만으로 스캔을 배제해서도 안 됩니다. 일반 Mac 처리량 비교는 기존 60초 대기를 유지하고, 재연결·절전 복귀 직후 동작은 별도 시험으로 기록합니다.

첨부 `R32_RECOVERY_DIAGNOSTIC.json`, `R32_FRESH_ASSOC_SCAN.json`에 수치와 한계를 추가했습니다. 이 진단 때문에 커널·드라이버·펌웨어를 변경하지 않았습니다.

## Air 실물 검증 — 2026-09-25

r32 커널 + `bridge-flow-offload 1.0-r3`에서 iPhone Air의 5+6GHz MLO 다운로드를 5분간 측정했습니다. 유선 서버는 2.5Gbps이며 4개 TCP 스트림, 미러링 없이 화면을 켜고 위치를 유지했습니다.

- 아이폰 iPerf 보고값: **평균 1,979Mbps / 최저 1,784Mbps / 최고 2,035Mbps**.
- 공유기 LAN2의 시험 내부 약 1초 구간 292개에서 전송량 0 및 500Mbps 미만 구간은 각각 0개였습니다. LAN2 전체 입력량은 아이폰 앱의 유효 처리량과 구분합니다.
- 전체 CPU 사용률 평균 **8.45%**. 시험 내부 가속 표본 **52/52회** 모두 네 흐름과 양방향 PPE 항목 8개를 확인했습니다.
- 전체 링크 표본 100회에서 두 링크와 WCID를 유지했습니다. 유선 확인 **552 통과 / 0 실패 / 0 경고 / 0 생략, 통과율 100%**. 설정·부팅 상태는 동일했고 시험 구간에 새 커널 메시지는 없었습니다.
- 전송 상태 카운터 증가는 6GHz에서 관측됐고 5GHz는 절전 상태였습니다. 두 링크 동시 합산 성능을 입증한 결과는 아닙니다. NPU의 빠른 descriptor 대기 주소 표본 1개는 관측됐지만 전송량 0 구간은 없어 펌웨어 정지로 판정하지 않습니다.

첨부 `R32_AIR_MLO_VALIDATION.json`에 수치와 한계를 보존했습니다. 기록기 준비 과정의 두 시도는 제외했고, 첫 표본 저장 확인과 전체 시험 구간 포함 검사를 통과한 회차만 사용했습니다. 아이폰의 별도 멈춤 진술과 앱의 원시 초별 보고서는 없으며, 이번 한 회차로 과거 간헐 멈춤·절전 복귀·장기간 안정성을 해결 완료로 판정하지 않습니다. r33 전체 이미지 설치·부팅은 여전히 미시험입니다.

### Air 절전 복귀 비교 — 짧은 멈춤 미해결

같은 연결에서 화면을 잠근 뒤 135.89초 동안 두 링크를 기록했습니다. 25개 표본 모두 두 링크를 유지했고 22개 표본에서 두 링크가 PS1이었습니다. 절전 관측의 유선 확인은 134/134 통과했습니다.

잠금을 풀고 같은 5분 다운로드를 반복한 iPerf 보고값은 **평균 1,914Mbps / 최저 0Mbps / 최고 2,041Mbps**, 사용자 진술은 **“잠깐 멈춤”**입니다. 기록 무결성 검사는 통과했지만 **절전 복귀 안정성 결과는 실패**로 보존합니다.

LAN2 집계에는 시험 시작 약 21.48초 뒤 1.03초 구간에서 약 185Mbps로 떨어진 기록이 있습니다. 해당 구간 CPU는 3.95%였고 가장 가까운 가속 표본(구간 중심보다 약 0.50초 뒤)은 네 흐름·PPE 8개를 유지했습니다. 전체 시험 평균 CPU는 7.55%, 가속 표본은 52/52회 정상, 유선 확인은 551/551 통과했으며 새 커널 메시지는 없었습니다.

집계 기록의 0 전송 구간이 없다는 이유로 사용자가 본 멈춤을 배제하지 않습니다. 앱의 원시 초별 기록과 정확한 멈춤 시각이 없어 위 저하와 같은 사건인지는 확정하지 않습니다. NPU 의심 대기 주소 표본은 없었지만 표본 사이의 짧은 정지도 배제할 수 없습니다. CPU 포화가 이번 집계 저하를 설명하지는 않으며, 절전·스캔·드라이버·펌웨어 중 원인은 아직 미확정입니다. 첨부 `R32_AIR_WAKE_VALIDATION.json`에 실패 결과와 관측 한계를 추가했습니다.

### Air 6GHz 단일 링크 절전 복귀 비교

같은 Air를 6GHz 단일 링크로 바꾼 뒤 화면 잠금 상태를 135.68초 기록했습니다. 절전 표본 25/25에서 PS1이었으며, 복귀 후 같은 5분 다운로드의 iPerf 보고값은 **평균 1,860 / 최저 410 / 최고 2,034Mbps**입니다. 사용자는 **“속도만 낮아짐”**이라고 확인했습니다. 기록 무결성과 복원은 통과했지만 일시적 저하는 **WARN**으로 남깁니다.

시험 시작 7.16초 뒤 LAN2 전체 입력이 1.02초 동안 **0.071Mbps**로 거의 없어졌습니다. 문자 그대로 0은 아니며 앱의 초별 수신량과 같은 지표도 아닙니다. 이때 전체 CPU는 4.68%, 시험 평균은 9.52%였습니다. 앞뒤 가속 표본은 네 흐름·PPE 8개와 PS0을 유지했고, 시험 내부 표본 52/52회 모두 정상 등록 상태였습니다. 표본 사이의 순간 변화는 배제하지 않습니다.

MLO와 단일 6GHz 절전 복귀 양쪽의 초반 표본에서 비정상 TXFREE 상태 증가가 관측됐습니다. 정상 MLO 비교와 세 시험의 60~290초 표본 구간에서는 증가가 없었습니다. **공통 6GHz 송신 경로의 단서**이며, 해당 카운터는 패킷 손실률이나 펌웨어 결함의 확정 증거가 아닙니다.

시작 약 241.52초 뒤 다른 단말의 연결 해제 메시지 2개와 FDB 삭제 `-ENOENT` 메시지 2개가 있었습니다. Air의 연결은 유지됐고 해당 시각 전송은 약 2Gbps여서 앞선 7초대 저하와 겹치지 않습니다. 별도 정확성 점검 항목으로 보존합니다.

유선 확인은 절전 **135/135**, 복귀 기록 **557/557**, 전환·시험 제어 **980/980** 통과했습니다. 각 범위에서 실패·경고·생략은 0건이며 통과율 100%입니다. 제어기의 복원 대기 시간은 반복 HTTP 검사 개수에 포함되지 않으며, 복원 직후 별도 검증했습니다. 원래 MLO·가속 설정의 해시, 변경 없는 network·firewall·부팅 상태, 두 MLO AP 링크와 유선 carrier를 확인했습니다. 첨부 `R32_AIR_SINGLE6_WAKE_VALIDATION.json`에 수치·제한을 추가했으며 새 펌웨어는 설치하지 않았습니다.

## 남은 확인

Air의 과거 멈춤 해결, 실제 WCID가 바뀌는 재연결, 재연결 직후 일시적인 속도 저하, 절전·장기간 안정성은 미확인입니다. Mac의 5분 업로드·다운로드는 통과했지만 최대 속도와 MLO 링크 합산 성능을 입증한 릴리스는 아닙니다.

r33은 r32 커널 ABI를 사용합니다. r30/r31 또는 다른 빌드의 모듈을 혼용하지 마세요. 가속은 명시적으로 선택한 신뢰 포트 쌍의 IPv4 TCP 범위이며 VLAN·IPv6·UDP로 확대하지 않았습니다.
