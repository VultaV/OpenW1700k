## 직접 확인된 현상

- Linux 서버 캡처의 회전 파일 3개, TCP 기록 **1,728,003개**, 커널 캡처 drop **0개**를 회수·해시 검사했다. 실제 iperf 데이터 4개 연결과 SYN/FIN, 서버 프로세스·연속 표본을 대조했다. 원시 패킷은 비공개다.
- 서버 첫 데이터 이후 **22.913048–24.122492초**, 네 연결 모두 ACK가 없는 구간이 **1,209.444ms**였다. 23.311732초 서버 표본에서는 네 연결의 `cwnd=1`, `backoff=1`이었다. 수신 윈도우 0은 패킷과 서버 표본 모두 없었다.
- Mac iperf의 23.005031–24.003930초에는 네 흐름 모두 수신 0바이트였다. 서버의 iperf 구간 보고도 정체를 기록했다. 서버 패킷 시계와 Mac 시계를 별도로 교정하지 않았으므로 이 소수점 시각을 정확한 동시점으로 결합하지 않는다.
- 100ms가 넘는 네 연결 동시 ACK 공백은 **108개**, 합계 **18.329278초**였다. 공백 길이 중앙값은 **137.5105ms**, 시작 간격 중앙값은 **524.668ms**였다. 1초 처리량이 0인 구간 하나 외에도 짧은 정체가 반복된다.
- 서버 iperf CPU는 한 코어 기준 평균 **3.153%**, 최대 표본 **3.964%**, cgroup throttle 증가는 0이었다. 공유기 CPU 전체 평균은 **5.787%**였다. 현재 표본은 서버·공유기 CPU 포화를 지지하지 않는다.
- 전송 중 대상 TX PHY 표본은 2401.9Mbps/160MHz/2 NSS이고 MLO 링크는 `0x6`이었다. 네 데이터 흐름의 `HW_OFFLOAD`와 PPE 등록을 확인했다. 표본 사이 모든 패킷의 경로를 보장하는 값은 아니다.

## 원인 후보와 제한

Mac 진단 로그에는 시험 직전 AWDL 채널 일정이 `[36 36 149 149 36 36 36 36 36 36 149 149 36 36 36 36]`으로 바뀐 기록이 있다. 주기적 ACK 공백과 단말의 무선 채널 공유 동작은 함께 검증할 유력한 가설이다. AWDL이 AP 통신과 채널을 공유할 수 있다는 배경은 [프로토콜 분석 논문](https://arxiv.org/abs/1808.03156)에 있지만, 논문의 구형 구현을 현재 Mac의 정확한 시간표로 간주하지 않는다. 실제 RF 체류·슬롯 위상·연속 PS 기록이나 AWDL 조건을 바꾼 대조시험이 없어 원인으로 확정하지 않는다.

다른 station의 관측된 host 트래픽은 최초 회차보다 작았지만, 이 카운터는 offload 트래픽 전체나 airtime을 뜻하지 않는다. 최초의 큰 host background 부하만으로 이번 저하를 설명할 수는 없다. 대상 RED 상태2 증가 11,477과 TCP 재전송 보고 19,225도 관측했으나 서로 같은 패킷 개수로 해석하지 않는다.

r43의 NPU guard는 양수 예산 경로에서 확인된 상태 차이가 없다. 다만 예산 0에서 조기 반환한 뒤 caller가 DMA index를 다시 읽는 빈도와 backpressure의 실제 성능 영향은 미검증이다. guard 실행 횟수·ring 여유·DMA 진행을 정체 시점에 기록하지 않았으므로 r43 회귀 가능성도 배제하지 않는다. 현재 결과만으로 guard를 되돌리거나 새 펌웨어 수정을 확정하지 않는다.
