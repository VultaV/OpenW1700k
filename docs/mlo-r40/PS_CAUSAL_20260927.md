# r40 Mac 절전·TCP 상관 분석

2026-09-27. 같은 r40 부팅·MLO 연결에서 Wi-Fi 설정 화면 열림 60초와 닫힘 60초를 비교했다. **열림의 반복 저하와 host가 받은 절전 전이가 함께 나타났다. 최초 손실의 원인이나 AP 내부 복귀 지연은 아직 확정하지 못했다.**

## 실제 측정

| 조건 | 수신 평균 Mbps | 1초 최저 Mbps | 서버 TCP 재전송 | 유선 HTTP 정상 확인 |
| --- | ---: | ---: | ---: | ---: |
| 설정 화면 열림 | 1238.9 | 45.2 | 15822 | 77/77 |
| 설정 화면 닫힘 | 1958.6 | 1819.9 | 5689 | 77/77 |

두 회차 모두 네 TCP 데이터 흐름의 PPE bound fastpath, 시작·종료 MLO bitmap `0x6`, 동일 설정·부팅을 확인했다. 0Mbps인 1초 표본은 없었다. 시험 무결성 검사는 **2 PASS / 0 FAIL / 0 WARN / 0 SKIP, 100%**이며 성능 문제 해결 판정과 구별한다. 기존 PS 진단만 켰고 새로운 펌웨어·무선 정책은 적용하지 않았다.

## 시각과 절전 기록의 한계

Mac 시각으로 공유기의 `/proc/uptime` 응답 왕복을 감싼 표본 20개를 보존했다. 0.01초 반올림/절삭 불확실성을 포함한 공통 오프셋 교집합 폭은 **16.63ms**다. 같은 부팅과 suspend 부재를 전제로 하며, 이것은 실제 무선 이벤트의 정확도가 아니다.

iperf 데이터 시작 시각은 프로세스 생성 시각과 종료 관측 시각에서 실행 시간을 뺀 값 사이로 보수적으로 제한했다. 이 폭은 열림 **0.719초**, 닫힘 **0.548초**다. 공개 JSON의 상대 이벤트 시각은 두 불확실성을 모두 포함한다. 서버 출력은 별도의 서버 상대 시각이며 독립적인 서버 wall-clock 보정은 수행하지 않았다.

표시된 kernel record 1933개는 연속이고 전송 해시도 일치했다. 하지만 driver 방출 제한 때문에 전체 단말의 P 순번 사이 **232개**, F 순번 사이 **25개**가 누락됐다. P 1916개·F 9개를 실제로 관측했고 suppression 안내는 6개다. kernel record 연속성과 driver 내부 이벤트 완전성은 다르다.

시험 Mac과 다른 단말의 이벤트를 분리했다. 시작·종료 경계를 제외한 확실한 시험 내부에서 대상 Mac의 P는 열림 **682개**, 닫힘 **0개**였고, 열림의 gate=1 관측은 **171개**였다. 닫힘 0개는 모든 실제 무선 상태 변화가 없었다는 보증이 아니다. 짧은 PS 반복과 누락 구간을 연결해 수초 동안 연속 절전이었다고 계산하지 않았다. P는 firmware PS 통지에 따른 host 처리 뒤의 독립 WCID 읽기이며 원자적인 무선 상태가 아니다. F는 status1 보고로, 성공 송신 시각이 아니다.

## TCP 회복도 저하 시간에 포함된다

저장된 서버 출력의 전송률·혼잡 윈도(Cwnd)는 다음과 같다. 네 스트림의 전체 60초와 마지막 부분 표본을 검사했다.

| 서버 상대 구간 | 재전송 합계 | 스트림별 Cwnd | 서버 전송률 Mbps |
| --- | ---: | ---: | ---: |
| 25–26초 | 1343 | 164–214KiB | 62.9 |
| 28–29초 | 0 | 291–427KiB | 713 |
| 29–30초 | 0 | 378–510KiB | 1510 |
| 43–44초 | 43 | 297–424KiB | 357 |
| 44–45초 | 0 | 375–469KiB | 1250 |
| 45–46초 | 0 | 452–549KiB | 1540 |

저하 후 전송률 상승에는 TCP 혼잡 윈도의 회복도 포함된다. 이 구간의 PS 기록에는 누락이 있으므로 “절전 해제 뒤에도 공유기가 정체했다”는 결론은 내릴 수 없다. 최초 손실이 단말의 채널 부재, NPU/WA 대기, 무선 firmware 처리 중 어디서 생겼는지는 분리되지 않았다.

## 드라이버·NPU 경계

현재 host PS 처리는 WCID bit와 host TXQ 재예약으로 이어진다. bound PPE 경로는 그 host TXQ gate를 우회한다. CPU 우회 경로도 NPU가 활성화되면 `mt76_npu_dma_add_buf()`를 사용하므로 **PPE 우회 시험은 NPU를 제외한 시험이 아니다**. NPU 전역 STOP은 단말별 PS 복귀 수단으로 사용할 수 없다.

기존 급락 표본의 두 링크 PS=1/1과 PLE queued=0은 동시 host 관측이다. PLE 값은 NPU descriptor/token 또는 WA 내부 전체 대기열이 비었다는 증거가 아니다. 실제 scan/channel 로그, 누락 없는 대상 PS 기록, NPU/WA 내부 진행 상태가 다음 원인 판정의 경계다. 근거 없는 새 기능 패치로 원인을 확정하지 않았다.

## 상위 갱신 확인

9월 27일 06:39 KST 조회에서 미배포 UBI2 소스 HEAD는 [68878ee25e48](https://github.com/OpenWRT-fanboy/OpenW1700k/commit/68878ee25e48e49b020eb9d8279e52d1213f13df), kernel73은 [4bb619998f4f](https://github.com/OpenWRT-fanboy/OpenW1700k/commit/4bb619998f4f47f73770a7228ac9af69cdcad0dd)다. 재기반화로 merge-base 변경 목록이 부풀려져, 이전 배포 핀과 각 Git tree를 직접 비교했다. 실제 변경 13파일은 mtd TRX 오류 경로, libpcap 1.10.7, tcpdump 4.99.7, elfutils 0.196, Mercusys MR90X SPI-NAND다. mt76·hostapd·Airoha·펌웨어 변경은 없었다.

[배포 UBI2](https://github.com/w1700k/builds/releases/tag/ubi2_2026.09.26_r36602-54e453b074)와 [kernel73](https://github.com/w1700k/builds/releases/tag/kernel73_2026.09.26_r36605-710dd8fa84) 이미지는 직전 재게시 기록과 같았다. [fastbuild](https://github.com/w1700k/fastbuild/commit/bb2e64fe333236fa72489743bb8c60a4d6f001cc), [mt76](https://github.com/openwrt/mt76/commit/be5ce7910521492d4a2e4ce7ee3843680a46c047), [Airoha 상위 변경](https://github.com/torvalds/linux/commit/4bdee8060d1e4581624e68fbd369b1afb14df4bc)도 이전 확인과 같았다. [linux-firmware 새 HEAD](https://kernel.googlesource.com/pub/scm/linux/kernel/git/firmware/linux-firmware/+/9b858e5bb58d7bf1fc4d8818cb9100aed6d46f6a/)에서 MT7996 tree 33항목은 이전 핀과 같고 NPU program/data도 기존 실제 blob과 같았다. 새 PS/RED/EMLSR 수정을 찾지 못했다.

[Discussion 34](https://github.com/w1700k/builds/discussions/34)와 [25](https://github.com/w1700k/builds/discussions/25)의 갱신 시각은 그대로다. [OpenWrt 포럼](https://forum.openwrt.org/t/gemtek-w1700k-community-builds/249319/473)은 접근 실패하여 갱신 여부를 확인하지 못했다.
