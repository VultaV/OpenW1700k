# r40 Mac 반복 저하: Wi-Fi 설정의 스캔 동작 확인

2026-09-27. 기존 실시간 `airportd` 수집기를 재사용하여 스캔·PS·속도를 함께 기록했다. **재현된 Mac 반복 저하에는 Wi-Fi 설정 화면의 주기적 네트워크 검색이 기여한다.** 같은 MLO 연결에서 그 화면을 닫자 평균 약 1.96Gbps로 회복했다. 이 결과를 원래 Air의 간헐 멈춤까지 해결한 것으로 확대하지 않는다.

## 재현과 제거

| 같은 연결의 조건 | 수신 평균 Mbps | 1초 최저 Mbps | 500Mbps 미만 표본 | 유선 HTTP 정상 확인 |
| --- | ---: | ---: | ---: | ---: |
| Wi-Fi 설정 화면 열림 | 985.5 | 58.6 | 26/60 | 77/77 |
| 화면을 General로 이동 | 1958.2 | 1751.8 | 0/60 | 77/77 |

두 회차 모두 MLO 링크 bitmap `0x6`, 네 실제 TCP 데이터 흐름의 PPE bound fastpath, 동일 부팅·설정을 확인했다. 무선 재연결이나 펌웨어 변경 없이 화면만 전환했다. 시험 무결성은 **2 PASS / 0 FAIL / 0 WARN / 0 SKIP, 100%**다. 이는 모든 성능 문제의 해결 판정이 아니다.

## 요청자와 실행 기록

열림 로그의 요청자는 `com.apple.wifi-settings-extension`이다. 전체 캡처에서 부모 `BEGIN REQ [SCAN]`가 6건 관측됐고 시작 간격은 **15.978 / 17.020 / 15.930 / 15.919 / 16.085초**였다. 이 가운데 앞의 5건은 동일 요청 ID의 완료 `err=0`을 확인했다. 마지막 요청은 기록 종료 경계에서 미완료다. 별도의 `BEGIN SUBREQ`를 중복 합산하지 않았다.

요청에는 53개 채널(2.4GHz 13개, 5GHz 25개, 6GHz PSC 15개)이 포함됐다. 별도 BEST CONNECTED 요청 1건에 따른 background 하위 요청 33건도 있으므로, 연결 직후 검색과 설정 화면의 반복 검색을 구분했다. 캐시 조회 요청과 실제 `SCAN` 요청도 구별했다.

`Perform live scan`의 진입·종료를 daemon thread별로 맞추면 완결된 **49쌍**, 캡처 끝의 미완료 진입 1건이다. 완결된 쌍 중 33개는 background, 16개는 Wi-Fi 요청 처리다. 실제 traffic 구간과 겹치는 완결 호출은 44개이며, traffic 중 설정 확장 프로그램의 부모 요청은 4개다. **이 수치는 함수 호출 수로 물리적인 무선 스캔 횟수가 아니다.**

프로세스 시작을 기준으로 설정 요청의 주요 처리 묶음은 **12.406–16.781초, 26.960–32.185초, 42.889–48.104초**다. Mac 데이터 시작은 프로세스 생성 뒤 0–0.710431초 사이여서 이를 포함해 대응시켰다. 500Mbps 미만 표본 26개 중 22개는 보수적인 시각 범위에서 스캔 함수 구간과 겹칠 수 있다. 나머지 4개는 약 17–21초이며 서버 TCP Cwnd가 작아진 뒤 회복하는 구간이다. 이 네 구간을 스캔 실행 자체로 설명하지 않았다.

화면을 닫은 캡처에는 해당 필터의 헤더만 있었고 일치하는 메시지는 관측되지 않았다. 이는 모든 가능한 무선 스캔이 없었다는 보증은 아니다. 동일 연결·펌웨어에서 요청자와 반복 주기를 식별하고 화면 전환 후 해당 로그와 저하가 함께 사라졌다는 점이, 이전의 단순한 저장 로그 부재보다 강한 증거다.

## 드라이버·펌웨어 해석

Mac–공유기 시계 보정 20표본의 공통 구간 폭은 17.33ms다. 실제 데이터 시작의 추가 불확실성은 열림 0.710초·닫힘 0.564초로 별도 보존했다. 스캔 함수 처리 시간은 RF off-channel 체류 시간과 다르다.

열림의 확실한 시험 내부에서 대상 Mac P 이벤트 821개, gate=1 관측 206개가 있었다. 닫힘에서는 같은 기준으로 대상 P가 0개였다. 다만 열림의 전체 단말 P 순번 사이 508개가 rate limit으로 누락됐다. 방출된 kernel record는 연속이지만 완전한 PS 전환 기록은 아니다. 따라서 최종 wake 이후 NPU/WA가 얼마나 기다렸는지는 확정하지 못했다.

현재 커널은 KPROBES/FTRACE/PERF_EVENTS를 지원하지 않고, 기존 PS logger에는 대상 WCID 필터나 rate-limit 조절 기능이 없다. 기존 host `token_info`와 queue 상태는 NPU 내부 consumer·잔여 HW token을 전부 보여 주지 않는다. `hw-queues`와 PPE 조회도 내부 selector/SRAM request를 써서 읽기 전용 파일이라고 무부하 관측은 아니다. 원인 증거 없이 새 NPU STOP·PS 강제 awake·RED 조정을 적용할 근거는 없다.

## 적용한 조치와 남은 범위

재현된 Mac 검색 부하를 제거하려면 연결 선택을 마친 뒤 Wi-Fi 설정 화면과 네트워크 검색 목록을 닫고 일반 사용 상태에서 측정한다. 이번 시험은 **General 화면 전환**을 검증했으며 다른 검색 UI의 동작까지 시험한 것은 아니다. 보안·자동 연결·공유기 설정은 변경하지 않았다. 새 firmware 수정이나 r 버전 상승도 없었다.

PS 진단·console 값과 기존 공유기 설정이 복원됐고 Mac의 원래 핫스팟 인터넷·유선 관리 접속도 확인했다. r40은 여전히 실험 prerelease다. 이 결과로 이미 재현한 Mac UI 검색 저하를 별도 분류하고, 다음 판단은 검색 화면이 닫힌 일반 사용 조건의 남은 증상에 한정한다. 원래 Air의 간헐 멈춤과 모든 장기 안정성은 미검증이다.
