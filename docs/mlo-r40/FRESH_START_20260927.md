# r40 새 연결 초반 저하와 같은 연결의 대조 — 2026-09-27

**Mac Wi-Fi 설정 화면에서 벗어나도 새 연결 초반 저하가 재현됐다.** 이 구간에는 별도로 예약된 macOS AutoJoin의 background scan, AP의 host PS 전이와 TCP 혼잡 윈도 감소가 함께 있었다. 같은 연결을 유지한 다음 측정은 안정적이었다. 설정 화면을 닫으면 모든 스캔·초기 저하가 사라진다고 일반화할 수 없다.

|---|---:|---:|---:|---:|---:|
| 새 연결 직후 | 18초 | 1497.21 | 71.55 | 2001.95 | 12 / 0 |
| 같은 연결 유지 후 | 231초 | 1951.52 | 1823.74 | 2014.60 | 0 / 0 |

네 번의 station snapshot에서 association 시각과 대상·두 링크 `0x6`이 같았다. 두 사전 확인의 간격은 212.247초로 연결 나이 증가와 일치한다. 새 시험은 절전 상태의 Mac 시스템을 깨운 시험이 아니다. 각 시험에 새로운 TCP 연결 4개를 사용했다.

## 초반 검색의 요청자

연결 전부터 native airportd 로그를 수집했다. 전체 로그의 Wi-Fi 설정 확장 부모 SCAN 요청 3개와 milod 요청 6개는 각각 BEGIN/END가 맞고 모두 성공 완료됐다. 마지막 설정 부모 요청은 General 화면 확인 후 기록한 arm보다 **10.429초 전**, iperf 프로세스 시작보다 **16.088초 전**에 끝났다. arm이 정확한 화면 전환 시각이라는 뜻은 아니다.

별개로 AutoJoin의 BEST CONNECTED SCAN이 20초 뒤 실행하도록 예약됐고 **20.004초 뒤 request가 기록**됐다. 뒤따른 background live-scan 호출은 33쌍이며, 이 중 24쌍이 전송과 겹칠 수 있는 구간에 있다. 마지막 API 종료는 iperf 프로세스 시작 후 9.743초였다. 전체 완결 live 호출 46쌍은 daemon 표기상 background 33 / Wi-Fi 7 / milod 6이다. Wi-Fi의 하위 호출 7개를 부모 요청 3개와 일대일 대응시킨 수치가 아니다.

따라서 이번 전송 중의 검색을 **아직 끝나지 않은 설정 화면 부모 요청**으로 설명할 수 없다. AutoJoin 예약·실행은 확인했지만, 연결 callback·RNR·neighbor report 중 무엇이 예약을 촉발했는지는 로그에 명시돼 있지 않다. 검색 API의 실행 구간은 실제 RF off-channel 체류 시간도 아니다.

## 검색 뒤의 저하도 모두 NPU 정지로 볼 수 없는 이유

- 500Mbps 미만 12개 표본 중 8개는 API 호출과 시간 불확실성을 고려하면 겹칠 수 있다. 나머지 4개 저하 표본까지 스캔 API 실행 시간만으로 설명하지 않는다.
- 마지막 API 종료 뒤에도 프로세스 기준 약 10.091–12.347초에 대상의 두 링크 PS 상태가 전환됐다. 약 10.372초 dip snapshot은 두 링크 PS=1/1, PLE 큐 AC02(WMM0/AC2)의 조회값 queued=0이었다. 이때 실제 네 데이터 흐름의 HW_OFFLOAD와 양방향 PPE BND를 확인했다. binding과 이 PLE 큐 조회값는 실제 모든 NPU 내부 패킷 진행의 증명이 아니다.
- 서버 TCP 10–11초 구간은 약 69Mbps·재전송70회·흐름별 CWND 약 124–460KiB였다. 11–14초에는 재전송0이어도 332/423/318Mbps 수준에 머물렀고 이후 전송이 회복됐다. TCP 구간과 수신 구간은 시작 기준이 완전히 같지 않다.
- 전체 단말 P 기록 1,094개에서 순번 누락273개가 있었다. 특히 마지막 연속 PS 관측 뒤 누락119개가 약 12.347–36.339초를 가로질러, 최종 wake부터 회복까지의 시간을 확정할 수 없다. 방출된 kernel 기록 자체는 연속이었다.
- CPU 평균 사용률은 약5.5%, 표본 중 최대 단일 코어 사용률은 약12.0%였다. CPU 포화로 이 저하를 설명할 증거는 없다.

새 연결의 보장된 전송 내부에서 대상 P 기록314개, host TXQ gate=1 기록79개가 있었다. 대조에서는 대상의 추가 P 전이가 전송 내부에 없었고, 전체 단말 P652개는 첫/끝 사이 누락0이었다. 대조 native 로그에는 헤더만 있고 scan 호출·요청·reader drop 표시는 없었다. 이는 **이번 로그에 관측되지 않았다**는 뜻이며, 모든 RF 검색이 없었다는 증명이 아니다.

TX drop status2 누계는 첫 시험 전후 0→906, 대조 전후 906→906이었다. 서버 TCP 재전송은 각각 2506/1964회로, 고속 대조에도 재전송은 있었다. 특정 상태 코드의 증가와 저하가 같이 관측됐다는 사실만으로 RED·NPU가 원인이라고 판정하지 않는다.

## 검증·복원과 남은 범위

실제 네 TCP 데이터 흐름의 PPE 경로, 각 회차 유선 HTTP77회(합154회) 정상, 서버2.5Gbps·Mac 관리1Gbps, 같은 boot/config를 확인했다. 두 회차 시계 표본20개는 폭16.491ms의 공통 offset과 양립했다. 데이터 시작의 별도 불확실성 폭은 각각0.648/0.541초로 보수적으로 반영했다. 로그 reader stderr·drop 표시는 없었다.

진단 guard는 두 회차 모두 RESTORED, PS trace와 강제 awake 시험은 OFF, console은 원래 값, UCI 미적용 변경은 없었다. Mac은 원래 iPhone 핫스팟과 General 화면으로 복원했고 핫스팟 HTTPS와 유선 관리 연결도 정상 확인했다. 펌웨어·무선 설정·PPE 규칙 변경이나 재부팅은 하지 않았다.

**관측 결론:** 이 새 연결 저하에는 예약된 background 검색과 host PS/TCP 변화가 겹치며, 시간 경과 후 동일 association에서 정상화된다. 순차 한 쌍과 일부 누락된 PS 기록만으로 검색의 단독 인과관계, 완전히 awake인 상태의 NPU/WA 정지, 원래 Air의 간헐 멈춤 해결 여부를 확정할 수 없다. 기존 RRO 오류 처리 결함도 별도로 남는다. 새 제품 패치·r 버전은 만들지 않았다.
