# r42 서버 시각을 포함한 PS·TCP 비교

2026-09-27, 설치된 r42의 Mac 재연결 시험. **마지막 host PS 조건 해제 뒤 네 TCP 흐름 모두 시계 오차를 포함해 20.709ms 안에 누적 ACK가 전진했다. 이후 100ms 이상 ACK 진행 공백은 없었다.** 이번 기록은 해제 후 수초간 멈추는 host TXQ 결함을 뒷받침하지 않는다. 원래 Air의 간헐적 절전 복귀 문제는 해결 판정하지 않는다.

## 조건과 관측

Mac 설정은 General 패널로 옮긴 뒤 시험 내내 유지했다. 이전 Wi-Fi 패널을 열어 둔 회차와 원본을 구분해 보존했다. AP·유선 설정과 펌웨어는 바꾸지 않았다. 같은 두 MLO 링크, 새 association, 네 흐름의 PPE 가속 등록을 확인했다.

4개 TCP 다운로드 흐름에 각각 150Mbps를 지정해 40초간 측정했다. 전체 목표는 600Mbps이며 최대 속도 시험이 아니다.

| 항목 | 결과 |
|---|---:|
| 평균 / 최저 / 최고 | 599.963 / 62.669 / 1,592.709 Mbps |
| 500Mbps 미만 / 0Mbps인 1초 구간 | 13 / 0 |
| iperf 서버 재전송 보고 | 3,323 |
| 네 흐름 동시 ACK 공백 100ms 초과 | 56구간, 합계 8.873초 |
| 최장 동시 ACK 공백 | 348.850ms |
| 캡처 / kernel drop | 395,656 / 0 |
| 서버 프로세스 CPU 평균 / 표본 최대 | 3.526% / 5.945% |
| 컨테이너 CPU 제한 횟수·시간 증가 | 0 / 0 |
| 수신 윈도우 0 ACK | 0 |

CPU 100%는 한 코어 기준이며 서버 표본은 1초 간격이다. veth의 GSO 기록은 물리 패킷 수가 아니다. TCP 헤더·옵션과 실제 네 연결을 확인했으며, 정상 종료 FIN의 sequence 1byte는 payload 진행 집계에서만 제외했다. 마지막 데이터는 네 흐름 모두 ACK됐다.

## 시계 경계와 PS 해제 후 전달

유선 연결로 시험 전후 PVE–Mac 시각을 각 10회 측정했다. 요청과 응답의 네 소프트웨어 타임스탬프를 사용했고, Mac에 저장한 20개 응답이 PVE 기록과 정확히 일치했다. 시간 변경이나 지속 서비스는 사용하지 않았다.

- PVE–Mac offset 교집합 폭: **0.470ms**.
- Mac–공유기 10회 측정의 offset 폭: **19.573ms**. `/proc/uptime`의 10ms 절삭 오차를 포함한다.
- 두 경계를 합친 PS→서버 패킷 시각 오차 폭: **20.044ms**.
- 양쪽 호스트의 wall/monotonic 전후 검사 통과. 일정 offset 모델과 양립한다는 뜻이며, 구간 내 물리적인 drift가 없다는 증명은 아니다.

iperf 실행 시작의 넓은 시각 범위를 거치지 않고 서버 패킷 시각과 공유기 uptime을 직접 비교했다. 전역 P 전이 **938건**, 내부 순번 누락 **0**이며 대상 상태 **722건**의 링크·old/new·gate 일치를 검사했다. 실제 데이터 창 안에서 완결된 두 링크 절전 구간은 **162회**, 합계 **12.667초**, 최장 **340.026ms**다.

마지막 host gate 해제는 서버의 첫 실제 데이터 이후 **32.298–32.318초**에 대응한다. 이후 네 흐름에 확실한 ACK 진행이 존재하는 지연 상한은 각각 **20.630 / 20.629 / 20.709 / 20.705ms**다. 뒤의 전송 구간에서 흐름별 ACK 진행 공백은 최대 **29.823ms**였고 100ms 초과는 없었다. 시계 오차 범위 안에도 ACK가 있으므로 이 값을 ‘최초 무선 송신 성공 지연’이라고 부르지 않는다.

최장 동시 ACK 공백 **348.850ms** 중 host gate가 닫힌 구간과의 교집합은 **310.750–314.616ms(89.077–90.187%)**다. 하나의 공통 offset을 모든 구간에 적용하고 오차 범위 전체에서 최소·최대를 계산했다. 이 공백에는 여러 절전 구간이 겹친다. 앞서 집계한 최장 340.026ms 단일 절전과 같은 사건이라는 뜻도, host 조건이 가속 패킷을 직접 막았다는 증거도 아니다.

## 해석과 남은 범위

General 패널에서도 native 스캔 API 호출 39쌍이 기록됐다. association 후 약 20초에 예약된 스캔 요청이 있었고, Wi-Fi 설정 화면에서 요청한 기록은 없었다. API 호출 시간은 실제 RF 채널 체류 시간이 아니다. 단말의 반복 절전·스캔 활동과 초반 저하를 구분해 기록할 수 있지만, AP 펌웨어 버퍼나 RF에서의 실제 전달을 이 로그만으로 확정하지 않는다.

host gate는 알림 처리 후의 드라이버 조건이다. 가속 패킷이 이 조건을 매번 통과하는 것은 아니므로 절전 구간을 NPU 패킷 차단 시간으로 바꾸어 해석하지 않는다. ACK 지연도 순방향 데이터 지연과 역방향 ACK 지연을 구분하지 못한다. 따라서 이번 증거만으로 추가 wake 우회나 NPU 큐 강제 초기화를 넣지 않았다.

시험 중 유선 확인 **55/55 정상**, 이후 설정 **34/34 해시 일치**, 같은 부팅·진단 OFF·기존 PS 수정 ON을 확인했다. 서버 기록 프로세스는 종료됐으며 Mac은 기존 핫스팟으로 돌아가 해당 경로의 HTTP 200을 확인했다.

`CLOCK_ENDPOINT_DATA.json`에 입력 해시와 경계를 보존한다. 로컬 재검산은 같은 artifact의 `analyze.py`, `check-tcp.py`, `check-alignment.py`와 이전 회차의 `check-server.py`를 재사용한다. 원시 패킷·단말 식별자·설정 백업은 공개하지 않는다. 펌웨어 변경 없이 추가한 관측이므로 r42 태그와 이미지는 유지한다.
