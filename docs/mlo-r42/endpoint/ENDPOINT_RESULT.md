# r42 Mac 재연결: 서버 TCP와 절전 기록

2026-09-27. 설치된 r42에서 Mac의 새 5+6GHz MLO 연결을 시험했다. **서버 CPU 포화나 수신 윈도우 폐쇄는 이번 저하를 설명하지 못했다.** 단말의 스캔과 반복 절전 상태가 관측됐지만, 이것만으로 펌웨어 큐 결함이나 원래 Air 절전 복귀 문제의 해결을 확정하지 않는다. 펌웨어·AP·유선 설정은 변경하지 않았다.

## 시험 조건과 복원

- 4 TCP 흐름, 다운로드, 흐름당 150Mbps 목표, 40초. 최대 속도 시험이 아니다.
- **조건 차이:** 핫스팟 확인을 위해 연 Mac Wi-Fi 설정 패널을 이번 기록 동안 그대로 두었다. 기존 r42 시험 절차의 General 패널 조건과 다르며, 설정 UI가 추가 스캔을 유발했을 가능성이 있다. 이번 패킷은 해당 조건에서 발생한 실제 지연의 증거이며, 이전 닫힌 패널 시험과 평균·지속 시간을 직접 비교하는 대조군으로 쓰지 않는다.
- 연결 후 7.494–8.678초에 데이터 전송을 시작했다. 같은 association과 두 링크(0x6), 네 흐름의 PPE 가속 등록을 확인했다.
- 평균 **481.465Mbps**, 최저 **38.803Mbps**, 500Mbps 미만 23구간, 0Mbps 구간 0개. iperf 서버 보고 재전송은 **3,935회**다.
- 시험 중 유선 HTTP 확인 **55/55 정상**. 종료 후 설정 34개 해시 일치, 부팅 유지, 선택적 PS/BA/TX 진단 OFF, 원래 PS 수정 ON을 확인했다.
- Mac은 기존 핫스팟으로 복원했고 해당 무선 경로의 인터넷 HTTP 200을 확인했다. 서버 기록 프로세스는 제한 시간 후 종료됐다.

## 서버 병목 검사

두 iperf 서버 프로세스 중 실제 시험 포트를 연 프로세스를 선택했다. 140개 표본에서 PID와 시작 시각이 유지됐고, 실제 네 데이터 흐름이 함께 존재하는 표본 40개(첫·마지막 사이 39.422초)를 분석했다. 이전 수집기의 ‘가장 오래된 프로세스 선택’을 이번에는 소켓 소유자 확인으로 대체했다. 과거 결과가 잘못됐다는 뜻은 아니다.

| 항목 | 이번 기록 |
|---|---:|
| iperf 프로세스 CPU 평균 / 표본 최대 | 2.131% / 5.931% |
| 컨테이너 CPU 평균 / 표본 최대 | 3.319% / 6.723% |
| CPU 제한 횟수 증가 / 제한 시간 증가 | 0 / 0 |
| 네 흐름의 최소 congestion window | 122–137 MSS |
| 네 흐름의 최대 RTO 추정값 | 679–736ms |
| 네 흐름의 최소 광고 수신 윈도우 | 352,640–897,088 bytes |
| 수신 윈도우 0 표본 | 0 |

CPU의 100%는 한 코어 기준이다. RTO는 타이머 추정값이며 실제 timeout 발생 횟수가 아니다. `backoff` 필드는 관측되지 않아 null로 남겼다. 1초 표본은 짧은 변화나 호스트 전체 CPU 부하를 배제하지 못한다.

## TCP 패킷으로 좁혀진 범위

서버 veth에서 시험 단말·서버·포트로 한정한 패킷 **361,503개**를 수집했고 kernel drop은 **0**이었다. 네 데이터 연결의 SYN/SYNACK, 양방향 주소와 흐름, 모든 TCP 옵션을 검사했다. 361,455개는 데이터 연결 네 개, 나머지 48개는 iperf 제어 연결이다. 회수한 압축 파일과 서버 SHA256도 일치했다.

네 흐름에서 동시에 ACK가 없는 100ms 초과 구간은 **103개**, 합계 **15.417초**였다. **약 355ms의 동시 ACK 공백**이 두 번 뚜렷했다. 서버의 첫 데이터 기준 약 **18.241–18.596초**, **18.628–18.983초**다. 누적 ACK가 전진하지 않는 동안 이미 내보낸 미확인 sequence 구간이 남아 있었고 서버는 일부 데이터를 계속 보냈다. 활성 데이터 연결에서 수신 윈도우 0인 ACK는 **0개**, SACK를 포함한 ACK는 **20,095개**였다. 이는 서버 프로세스 정지·수신 윈도우 폐쇄보다 네 흐름이 공유하는 전달/ACK 경로의 지연과 잘 맞는다. 다만 순방향 데이터 지연과 역방향 ACK 지연은 이 한 지점 기록으로 구분하지 못한다.

이미 관측된 sequence 범위와 겹치는 전송은 합계 **5,697,880 bytes**였다. veth의 GSO 기록은 최대 payload **65,160 bytes**이므로 캡처 record 수를 실제 유선/무선 패킷 수나 재전송 횟수로 환산하지 않았다. 최대 약 6.2µs의 캡처 timestamp 역순도 별도로 보존했다. 일부 종료 시점 RST와 미확인 tail은 중간 장애로 분류하지 않는다.

**서버 시계는 Mac–공유기 시계 교정에 포함되지 않았다.** 위 서버 상대 18초를 아래 PS 상대 18초와 직접 맞추거나 355ms에서 PS 시간을 빼서 ‘복귀 지연’을 계산하지 않는다. 다음에 정확한 post-wake 지연을 주장하려면 서버까지 포함한 시계 교정 또는 같은 패킷을 관측하는 동기화 지점이 필요하다. 현재 기록만으로 NPU 큐, AP RF 송신, 클라이언트 수신 중 하나를 원인으로 확정하지 않는다.

## 공유기 PS 기록

전역 P 전이 1,943개의 내부 순번 누락은 0개다. 대상 1,118개는 old/new 전환과 링크 상태·host gate 일치 검사를 통과했으며 non-AQL 값은 모두 0이었다. 보장된 전송 창 안의 대상 P는 988개다.

전송 창 안에서 시작과 끝이 모두 관측된 두 링크 절전 구간은 **247개**, 합계 **20.054초**, 최장 **203.137ms**다. 마지막 완결 구간의 gate 해제는 TCP 상대 **35.303–36.487초**, 마지막 저하 구간 끝은 **36.005초**로 오차 범위가 겹친다. 해제 뒤임이 확실한 첫 전체 1초 구간은 **1,472.943Mbps**였다. 이후 다음 gate 닫힘까지 연속 gate=0 구간은 약 3.930초이며, 그 다음 닫힘은 전송 종료 경계와 겹쳐 앞의 완결 구간 집계에서 제외했다.

따라서 이번에도 **host gate가 열린 뒤 수초간 정체했다는 증거는 없다.** host callback 뒤의 상태 로그는 worker 실행 완료, 성공한 무선 송신, 펌웨어 큐 상태를 기록하지 않는다. 가속 패킷은 이 host TXQ 조건을 패킷마다 통과하지 않으므로 위 시간을 실제 NPU 패킷 차단 시간으로 해석하면 안 된다.

현재 연결 요청의 MLE에는 EML 필드가 없고, 동시 링크 수 encoded 값은 0이며 NSTR 링크 쌍 정보가 있다. AP의 EMLSR 지원 광고를 이 Mac의 EMLSR 활성 상태로 간주하지 않는다. 이 값은 연결 기능 정보이지 무선 동작을 직접 관측한 결과가 아니다.

## 재검산
