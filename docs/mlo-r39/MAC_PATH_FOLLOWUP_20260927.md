# r39 Mac 경로·유휴 후속 비교 — 2026-09-27

**가속 경로는 약 1.97Gbps로 복구됐고, Mac Wi-Fi 설정 화면을 열었을 때의 반복 급락은 CPU 전달 경로에서도 재현됐다.** 이 급락을 PPE 고유 장애나 TXFREE raw status 2만의 문제로 단정할 수 없다. r39 설치 이미지·태그·제품 소스는 그대로 유지했다.

## 같은 연결에서의 CPU 전달·PPE 가속 비교

MacBook의 동일 5+6GHz MLO 연결, 같은 위치와 내부 2.5GbE 서버에서 TCP 4스트림 다운로드를 각각 60초 측정했다. 두 링크는 유지됐지만 전송은 주로 6GHz였으므로 동시 합산 성능을 입증하지 않는다. “닫힘”은 System Settings를 General 페이지로 이동한 상태다.

| 경로 / Wi-Fi 설정 화면 | 수신 평균 Mbps | 최저 1초 Mbps | 500Mbps 미만 구간 | TCP 재전송 |
|---|---:|---:|---:|---:|
| CPU 전달 / 닫힘 | 1,160 | 1,013 | 0 | 453 |
| CPU 전달 / 열림 | 912 | 50 | 17 | 654 |
| PPE 가속 / 열림 | 1,281 | 45 | 15 | 12,336 |
| PPE 가속 / 닫힘 | 1,971 | 1,787 | 0 | 1,325 |

CPU 비교에는 시험 단말과 서버의 TCP만 기존 `flow add` 앞에서 제외하는 임시 규칙 두 개를 사용했다. 라디오·네트워크·서비스·flowtable을 재시작하거나 전체 conntrack을 삭제하지 않았다. **전역 NPU는 계속 활성**이다. CPU 전달과 host TX 준비를 거치는 경로를 비교한 것이며 NPU 전체 ON/OFF 시험이 아니다.

각 CPU 회차의 초반·중반·후반 10개 시점에서 실제 새 데이터 tuple 4개씩, 총 80개 표본의 conntrack 존재와 OFFLOAD/HW_OFFLOAD·양방향 PPE BND 부재를 독립 확인했다. 양방향 임시 규칙 카운터도 증가했다. 표본 사이 모든 패킷의 경로까지 증명하지 않으며, 5초 간격 추가 조회 부하가 CPU 회차에 포함돼 있다. 가속 회차는 기존 방식의 전송 중 표본에서 네 연결의 가속 등록을 확인했다.

- 설정 화면을 닫은 CPU 회차의 전송 중 CPU 평균은 약 63%, CPU0는 약 91%였다. 약 1.16Gbps의 CPU 전달 경로와 큰 CPU 부하가 함께 관측됐다. 추가 진단 부하가 있으므로 이를 무계측 최대 속도라고 단정하지 않는다.
- 화면을 연 CPU 회차는 약 16초 간격으로 급락했다. raw status 2 증가가 **0**인데도 500Mbps 미만 구간이 17개였다. PPE 가속 회차에서도 같은 화면 조건에서 저하가 재현됐고, 다시 닫자 평균 1.97Gbps·최저 1.79Gbps로 회복했다.
- 열림 가속 회차의 raw status 2 증가는 12,015였지만, 정상 속도의 마지막 닫힘 회차도 전후 카운터 구간에 271개가 있었다. 카운터는 전후 수집 시간까지 포함하므로 정확한 사건 시각이나 TCP 손실량으로 해석하지 않는다. upstream도 status 비영 여부를 실패 시도 집계에 사용하며, [공식 TXFREE 집계 변경](https://github.com/openwrt/mt76/commit/c27f01c4c834527adb584d0ef0b2d340565e977c)에 status 2 전용 PS 의미나 복구 계약은 정의돼 있지 않다.

현재 관측은 **Mac 설정 화면 조건이 재현 가능한 저하 요인**이라는 근거다. 실제 scan·무선 프레임 시각은 확보하지 못해 구체적인 채널 이탈/절전 메커니즘까지 확정하지 않는다. MT7996/NPU의 잠재 결함 전체나 Air의 과거 순간 멈춤 원인을 배제하지 않는다.

## 2분 유휴 이후 전송 재개

Mac을 깨어 있는 상태로 120.402초 유휴 유지한 뒤 120초 다운로드를 실행했다. 평균 **1952Mbps**, 최저 **1817Mbps**, 최고 **2019Mbps**였고 0Mbps·500Mbps 미만 1초 구간은 모두 0개였다. MCU PS 이벤트에서 두 링크의 실제 PS 진입·복귀와 gate 전이를 확인했다. 이는 **Wi-Fi PS 전이 시험이며 Mac 전체 시스템 절전·복귀 시험은 아니다.**

이 회차의 원제어기는 과거 종료 표식이 앞에 남아 있어 종료 코드 1로 끝났다. 실패 기록을 보존하고 현재 호출의 시작 시각을 대조한 뒤 과거 2,892줄만 제외해 기존 엄격 검사를 다시 적용했다. 현재 구간의 262개 연속 기록(PS 260개+표식 2개)과 진단 복원을 검증했다. 제어기는 이후 고유 표식으로 수정했지만 수정 후 동일 시험을 다시 실행한 것으로 표시하지 않는다.

## 복원과 검사 한계

4회 경로 비교의 유선 관리 확인 **298회**, 유휴 회차 **261회**가 모두 정상이었다. 공유기 부팅·설정은 같았고 LAN 서버 2.5Gbps·Mac 관리 LAN 1Gbps가 유지됐다. 임시 규칙 제거 후 원본 stateless 규칙 SHA256 일치와 `RESTORED`를 확인했다. PS 진단·강제 awake 옵션은 OFF, 콘솔 값은 원래대로다. Mac을 원래 iPhone 핫스팟으로 복원하고 인터넷 HTTP 200을 확인했다.

시험 준비 중 검증기 문제 두 건도 기록했다. 첫 번째는 nft 출력 빈 줄 때문에 적용 전에 거절됐고, 두 번째는 nft가 생략한 중복 조건 때문에 적용 직후 소유권 검증이 실패했다. 두 번째의 남은 규칙은 전체 내용·핸들·원본 구조를 확인한 뒤 두 개만 제거했다. 정규화 처리를 수정한 최종 guard에서 실제 준비·자동 정리가 성공했다. 로컬 guard 검사 **16 PASS / 0 FAIL**, 경로 검증 검사 **15 PASS / 0 FAIL**이며, 이는 무선 장애 해결률이 아니다.

속도 수치는 1초 집계이며 더 짧은 정지를 배제하지 못한다. 서버 동시 TCP 캡처와 전체 Mac 시스템 절전은 이번에 실행하지 않았다. **Air 절전 복귀 멈춤의 원인과 r39 수정의 인과적 해결은 여전히 미확정**이다. 민감한 원시 로그·주소·단말 식별자는 공개하지 않고 [검증 수치·증거 해시](MAC_PATH_FOLLOWUP_20260927.json)를 남겼다.

## 최신 공식 UBI2 재게시 비교

[공식 UBI2 릴리스](https://github.com/w1700k/builds/releases/tag/ubi2_2026.09.26_r36602-54e453b074)의 같은 태그에서 배포 파일이 교체됐다. 보존한 최초 이미지와 재게시 이미지를 비교한 결과, **전체 이미지는 서로 다르지만, 추출한 드라이버 모듈과 NPU·MT7996 펌웨어의 새 변경은 확인되지 않았다.** 이번 재게시만으로 MLO 장애가 해결됐다고 판단할 근거는 없다.

대상 파일은 `openwrt-airoha-an7581-gemtek_w1700k-ubi-squashfs-sysupgrade.itb`이며, 두 이미지 모두 22,180,671바이트다. 파일 크기와 태그가 같아도 내용은 같지 않다.

| 구분 | 이미지 SHA-256 |
|---|---|
| 최초 게시 | `3f474396b2f55781d02d05986767fb61847ab29ed5fd51ae5af835814a0e5e4e` |
| 재게시 | `ece027c6843e347ffe5bc5528027bbc7486cbde6ce3e66b3029989df35749a98` |

재게시 파일의 SHA-256은 저장한 GitHub 공식 asset digest와 일치했다. FIT의 kernel·device tree·rootfs 세 payload 해시도 유효했다. 이는 파일 무결성 확인이며, 장치 부팅이나 성능 검증을 뜻하지 않는다.

- **펌웨어·드라이버:** 비교한 펌웨어 12개는 모두 최초 이미지와 바이트 동일했다. NPU 프로그램·데이터, MT7996 WM·WA·DSP 및 ROM patch를 포함한다. rootfs 전체 파일 내용 비교에서 드라이버 모듈 변경은 없었다. 패키지 버전 변경도 없었다.
- **커널:** 두 이미지 모두 Linux 6.18.52이며, 압축 해제한 커널 길이는 각각 13,629,448바이트다. 다만 10개 구간에서 총 84바이트가 달라 커널은 바이트 동일하지 않다. 표시되는 OpenWrt GCC 빌드 revision도 `r36600-dca177310d`에서 `r36602-54e453b074`로 달라졌다. 이 기록만으로 84바이트 전부의 의미나 실행 코드 동등성을 단정하지 않는다. device tree는 동일했다.
- **rootfs:** 내용이 달라진 파일은 APK 공개키, 설치 DB, 스크립트 archive, `fastfetch`, `librespeed-go`의 5개다. APK DB의 변경 대상은 `base-files`, `fastfetch`, `librespeed-go`였다. 스크립트 이름의 패키지 해시를 정규화한 뒤 비교한 414개 항목의 본문 차이는 없었다.
- **공개키 교체:** `/etc/apk/keys/public-key.pem`의 SHA-256은 `65f70a974c33efa94ebfae272232758aa6cfee4c279d666563afefd2dfafb400`에서 `aa06639b5471dd3e761df3eb1d4b56af1aaceb8ae80a2300e9d02ff7c80eaec8`로 바뀌었다. 패키지 저장소와의 실제 서명 호환성이나 기존 장치의 키 전환 절차는 시험하지 않았다.

이번 비교는 내려받아 보존한 파일의 오프라인 검증이다. **재게시된 공식 UBI2 이미지는 공유기에 설치하지 않았다.** 별도로 설치·시험한 수정본 r39의 결과와 구분한다. 새 커널 패치의 효과나 Air 절전 복귀 장애 해결을 입증하는 시험도 아니다.
